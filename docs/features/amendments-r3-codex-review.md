2. **0054 schedule reconciliation can deadlock with legacy writes.** A direct leave can own the series owner's attendee tuple before `block_suspended_writes` takes that owner's account lock. Specify how the series path avoids waiting in these cycles while preserving the client contract, for example by taking legacy actors' account locks before row mutation or using a nonblocking lock with a clean retry of the entire reconciliation. Check the two orderings for owner leave versus deletion of an otherwise disposable occurrence and for owner edit versus regeneration. Prove the assignment case with a date that only becomes retained during assignment, in addition to the static override case. ## 5.0 Outings and the 6.3 itinerary read contract

**Approved with required changes.** Keep the Must Events dependency gate, private anchor table, live access checks, sole event FK on the anchor, atomic `removed` flag, and explicit veto behavior. The following requirements apply before the affected outing and itinerary schema work.

1. **Keep shared planning visible and redact the event-dependent schedule.** A member without current event access can see the group's authored window, shortlist, authored stop details and order, and the generic anchor flag. Suppress the computed schedule and route/verdict details for the anchored version when the member cannot read the event. A fixed event determines the following stop's timing, so even a different stop's computed arrival can expose the event's end. Apply this rule to current and historical versions, generated suggestions and time-zone defaults. An event's zone must not be copied into a shared field without the same authorization. Use an independent outing zone for shared planning and show event-local times only in the authorized anchor projection. Add API tests using two versions and a known event with a distinctive time/zone, including a generated time or suggestion on a non-anchor stop and a member who later loses access. [Outings A1.4](5.0.md#a14-the-anchors-lifecycle-for-every-way-an-event-can-go-away) · [6.0 persistence amendment](6.0.md#amendment-note-2026-11-12--the-itinerary-holds-no-event-reference)
2. **Account cleanup must include implicit profile locks and the final cascade.** `prepare_account_deletion` holds the profile `FOR UPDATE`. An outing RPC that holds the outing row first can wait on a profile FK key-share (for example, adding a member or vote), while closure waits on that outing. Take the relevant account locks before the outing lock on profile-referencing paths and recheck closure, or define another explicit order that removes the cycle. Enumerate profile references on guarded tables and the maintenance handling for each. Marking a membership `left` alone leaves its user FK in place, and `anchored_by ON DELETE SET NULL` still causes a guarded update at physical deletion. Pre-clean rows or references that would otherwise fire the guard in a later transaction, keep the anchor when only its author is deleted, and specify how an owned outing and its children are deleted. Maintenance must work with locked outings without reopening ordinary vote writes. Test real Auth/profile deletion after preparation in a separate transaction, including an owner, an anchor author, and a member with a vote racing closure. Keep the event-delete-versus-itinerary-save tests.

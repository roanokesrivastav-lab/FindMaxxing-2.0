## Contract

- **Objective:** one server-side way to ask "how long is the walk between these points", which
  returns the `LegResult` shape from 6.2 and never anything else. Behind it: a deterministic fake
  (demo and tests), a Mapbox walking client that is not live (no key; exercised only with stubbed
  responses), a documented GraphHopper stub, and "not configured". A timeout, an error or a
  malformed answer becomes `unknown`; it never throws through and never becomes a short walk. A
  memo that lives for one request only. A durable limit of 60 route validations per signed-in user
  per hour, reserved before any provider work, failing closed.
- **Allowed files:** `src/server/trips/` (new routing files only), `src/lib/abuseLimits.ts`,
  `src/server/limiters.ts`, migration `0095` (Trips lane, allocated by the integration owner in the
  2026-11-12 preflight), focused tests, this note and the ledger.
- **Prerequisites verified:** 6.2's `LegResult` contract (`78cc608`); the 0040 limiter and its demo
  twin; Codex's preflight of 2026-11-12 ("Approved. Start 6.1 independently. Use migration 0095").
- **Out of scope:** the planner entry point, its tools and itinerary persistence (6.3); any UI; any
  provider credential or live call; storing any provider result; non-walking routes (X3, Later).
- **Preflight:** done for the limiter migration (the approval above). Its conditions: reuse 0040 and
  its demo twin with one new action; key from the server-authenticated user; budget reserved before
  provider work; fail closed on limiter errors; parity check extended to the effective policy;
  earlier budgets and service-only grants preserved.

## Changes

- **`src/server/trips/routing/`** (new).
  - `types.ts`: `WalkingRouter` (`id`, `legs(points, { signal })`), using 6.2's `LegResult`.
    `measuredLeg()` builds a leg from two numbers or returns unknown. `describeRouter()` says
    whether times are measured: only a configured provider is; the fake is labelled an estimate.
  - `fake.ts`: the deterministic fake. Great-circle distance × 1.3 at 80 m a minute, rounded up to
    whole minutes. A leg that would cross a barrier goes by the fixture bridge that makes it
    shortest; with no bridge it is `no_route`. A point inside a no-route zone is `no_route`.
    `COLUMBUS_FIXTURES` draws the Scioto downtown with four bridges and one unreachable spot; they
    are approximate stand-ins, not map data.
  - `mapbox.ts`: Mapbox walking directions. **Not live.** It asks for no geometry and no steps,
    reads `duration` and `distance` per leg and drops everything else. HTTP errors, `NoRoute`, a
    wrong leg count, non-numbers and aborted requests each become `unknown` with a reason. Long
    plans go in pieces of 25 points.
  - `graphhopper.ts`: the named fallback as a stub that answers `not_configured`.
  - `index.ts`:
    - `resolveWalkingRouter()`: demo mode is always the fake. Otherwise a provider is used only when
      `WALKING_ROUTER=mapbox-walking` **and** `MAPBOX_WALKING_TOKEN` are both set; the public map
      token is never used. Anything else is "not configured": every leg unknown, none estimated.
    - `routeLegs()`: one bounded call (4 s). A router that hangs, throws or returns the wrong shape
      gives the caller well-formed unknown legs; legs are rebuilt field by field.
    - `withRequestMemo()`: remembers legs for the life of the object it returns, which is one
      request. There is no module-level store, and nothing is written to a database, the demo
      store, a log or a shared cache.
    - `routeForValidation(userId, requests, { limit, router })`: reserves one validation for the
      user first, then routes with one 8 s deadline and one memo. Over the limit, or limiter
      unreachable: it throws and no router is called.
- **Limit: 60 route validations per signed-in user per hour** (6.0 R-3).
  - `supabase/migrations/0095_route_validation_limit.sql` replaces `server_abuse_budgets` with the
    same ten earlier rows plus `route_validation`. No table, grant or other function changes.
  - `ABUSE_LIMITS.route_validation` in `src/lib/abuseLimits.ts`; the demo twin reads that table, so
    demo and SQL share the cap.
  - `limitRouteValidation(userId)` in `src/server/limiters.ts`: the key is an HMAC of the
    server-authenticated user id under `ABUSE_HMAC_SECRET`. Any failure to reach the limiter is
    `DataError("unavailable")`.
- **`.env.example`**: `WALKING_ROUTER` and `MAPBOX_WALKING_TOKEN`, empty, with a note not to set them
  without the owner's written decision on the provider's terms.
- **6.2 follow-up found here:** an exact zero-minute walk came out as `-0` (from `Math.ceil`). Fixed
  in the validator and in the fake, with a test.

Flags: none. Dependencies: none. Demo and Supabase: demo routes with the fake and limits with the
demo twin; Supabase mode limits through the SQL and routes nothing until a provider is configured.

## Adversarial review

- **A router that misbehaves.** Hanging, throwing, the wrong number of legs, a string where a number
  belongs, extra fields on a leg: each is covered, and none reaches the caller as a walk or as data.
- **Sanity bounds.** A leg of more than a day or more than 200 km is treated as a bad answer.
- **The first version of one break did not fail a test.** "Public token used for routing" only
  changed the condition, not the token passed on, so behaviour was the same. Rewritten to really use
  the public token, it fails the configuration test. Recorded because a surviving mutation is worth
  saying out loud.
- **Budget order.** The reservation is taken before any routing and is spent even if routing then
  fails, as 0040's other limits are. A user cannot get a free retry loop out of provider errors.
- **Demo store.** The demo limiter writes its counter to the demo store, as every other demo limit
  does; the key there is the HMAC, not the user id.
- **Token in the URL.** Mapbox takes its token as a query parameter. The URL is built inside the
  client and never logged or returned. It matters only once a provider is configured.

## Remaining issues

- **Nothing calls the router.** The planner's `distance` tool still returns a straight-line walking
  estimate and a driving estimate (`src/server/trips/tools.ts`). Removing the driving figure and
  routing through this module were left for 6.3, as the preflight asked ("keep the current planner
  entry point").
- **NOT VERIFIED: Mapbox itself.** No key exists and no call was made. The request shape and the
  response fields are from the spec's reading of the public API, exercised on stubs only. The
  provider's terms for stored results are still unconfirmed by the owner (6.0 §2).
- **NOT VERIFIED: hosted database.** 0095 ran on PGlite and on local PostgreSQL only.
- The Columbus fixtures are rough. They exist so demo plans show a river detour, not to be right.
- `routeForValidation` needs the caller to pass the user id it authenticated; 6.3 must take it from
  the session, never from the request body.

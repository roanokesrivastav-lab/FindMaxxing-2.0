# 2.8 Public and private place photos

Built 2026-11-05, lane B2. Ticket: roadmap-80.md §4 M2 "2.8"; founder-decisions.md "Public and private place photos"
and the owner answers Q3–Q5. Flag: `pilotExplore`. Migration: `0063_personal_photos.sql`.

## Naming

"Private place photos" already means 0005's `place_photos`, whose objects follow place visibility (readable by anyone
who can see a public place). The new owner-only photo is called the **personal photo** everywhere (table
`personal_place_photos`, bucket `personal-photos`, route `/api/personal-photos/[placeId]`, UI "Your photo · Only you").

## Contract

- **Public photo:** each place has one public photo, uploaded by the team or with permission, with who set it and the
  permission note. No online provider. It leads the place page and cards.
- **Personal photo:** a user's first rating or review of a place requires one photo, which becomes their personal photo
  for that place: only they ever see it, and they see it in place of the public photo unless they change it.
  Self-declared, a library photo is allowed. It never blocks saving, planning, joining, bulk marking Visited, or imports.
- **Friend went, you didn't:** the public photo plus that friend's own review and the photos they chose to post.
  Personal photos are never shared, including with friends, outings, shares and recommendations.
- **Lane rule:** the existing place-photos bucket and `place_photos` policies are public for public places, so personal
  photos must not use them. Private bucket, owner-only access, signed URLs, keep metadata stripping. Test anon, owner,
  another user, a friend and a moderator, including direct API and storage calls. The no-photo page stays complete.

## Choices recorded (recommended option taken)

- **Storage:** new private bucket `personal-photos` (WebP only, 5 MB). Objects live under `<owner id>/…`. Four storage
  policies (select, insert, update, delete) admit exactly `foldername[1] = auth.uid()`: no moderator, admin, friend or
  place-owner clause. Uploads also pass `count_personal_upload()` (account closing / suspended checks, the existing
  `photos` hourly limit); 0030's `count_upload` is not modified.
- **Table:** `personal_place_photos (user_id, place_id, storage_path)`, one per user and place, owner-only RLS for every
  operation, no anon privilege at all, a check that the path is in the owner's folder, insert only for places the owner
  can see. No function, view or notification reads it (tested against the catalog).
- **Delivery:** `/api/personal-photos/[placeId]` has no user in the URL; it is always the viewer's own photo. Supabase:
  302 to a **signed URL valid 300 s**, minted with the owner's session (so storage policy re-checks the owner). Demo:
  bytes after the owner check. Everyone else gets the same 404 as a missing photo. `Cache-Control: private, no-store`.
- **Metadata stripping:** uploads go through the same pipeline as place photos (`preparePlacePhotos`: decode, orient,
  re-encode to WebP, drop EXIF/ICC/XMP). Only the main size is stored for personal photos.
- **First-rating requirement is enforced in `ratePlaceAction`, behind `pilotExplore`, not by a database trigger:** with the
  flag off ratings must behave exactly as today, and existing clients (the native app cannot upload a personal photo yet)
  must keep working. A direct PostgREST insert can therefore still rate without a photo; this is a product rule, not a
  security boundary. Changing an existing rating or note never needs a photo. On the page, a viewer who has not rated
  sees the stars disabled with the reason and an "Add your photo" button in the You block.
- **Never blocks:** saving, the save sheet, lists, bulk edit (including Visited), event joining and planning do not look at
  personal photos (tested for save, bulk visited and event join; imports do not exist yet).
- **Public photo:** `place_public_photos (place_id, photo_id, set_by, permission_note)`, readable wherever the place is,
  written only by `set_place_public_photo()` (moderators and admins, note required, photo must be one of the place's
  photos). The chosen photo is moved to sort order 0, so every card and page that leads with `photos[0]` leads with it,
  with no change to shared card code. The place page shows "Photo: <permission note>" on it. Until the team sets one,
  the first place photo leads, as today. Choosing photos needs the team to use the action/RPC; there is no admin screen.
- **Friends' posted photos:** in the Friends block, each friend's row shows up to three of the place photos that friend
  uploaded publicly. Personal photos are a different table and can never appear there.
- **Demo:** lazy collections; personal files are `personal-<owner>-<uuid>.webp` in the demo upload folder, which
  `/api/uploads` and `/api/photos` do not serve (their allowlists only accept `avatars-` / `places-`). Account deletion
  removes the files and rows (`placeExtras.ts`); in Supabase, `prepare_account_deletion` already collects every object
  under the user's folder in any bucket.
- **`RatingControl`** gained an additive `lockedReason` prop (default null: unchanged elsewhere).

## Test results

- `tests/personal-photos.test.ts`: 14/14.
  - Database (PGlite, storage RLS on, anon and authenticated granted table access as on Supabase): bucket private;
    **anon, another user, a friend (mutual follow), a moderator and an admin** cannot select, update or delete the row
    or the storage object (anon has no table privilege at all); nobody can upload into another's folder (including anon),
    insert a row for someone else, claim someone else's object (folder check), or add one for a place they cannot see;
    `can_view_place_photo_object` is false for it; no `public` function or view references it; account deletion's object
    sweep covers it; public photo: non-moderator and anon refused, note required, photo must belong to the place,
    becomes first, credit readable, no direct writes.
  - App (real actions, route and page on the demo repository): the route returns the owner's photo (200, WebP, **no EXIF,
    the planted EXIF text absent from the bytes**, `private, no-store`) and 404 to anon, another user, friend, moderator
    and admin; owner page leads with "Your photo · only you see it", every other viewer's page has no personal URL; share
    metadata, recommendations and another user's library have none; first rating refused with `photo_required`, existing
    rating changeable without a photo, rating allowed after upload; flag off rates as before; save, bulk Visited and event
    join succeed with no photo; the no-photo page is complete (glyph hero, every block, photo asked for and stars locked
    only for a first rating); friend who went: review plus posted photo, never the personal photo; team public photo leads
    with its credit; non-moderator refused.
- `npm run check` with `TEST_DATABASE_URL` set: **exit 0**, 86 files / 1,347 tests, none skipped, build OK.
- Browser (production demo build, 390×844): maya on Hollow Oak Print Studio (not yet rated): stars disabled with the
  reason, axe 0; uploading a JPEG carrying EXIF text through the real file input → hero switched to her photo with "Your
  photo · only you see it", stars unlocked; the route served her `image/webp` with the EXIF text absent; theo (signed in)
  and an anonymous client got 404 from the route, and theo's page HTML had no personal-photo URL.

## Could not verify

- **Hosted Supabase Storage:** the storage policies are tested against the PGlite storage stub (`storage.objects` with RLS),
  not real Supabase Storage; signed URL creation (`createSignedUrl`) and the 302 path are typechecked only. On staging,
  check: another user's JWT gets 400/404 for `GET /storage/v1/object/personal-photos/<owner>/<file>` and for
  `POST /storage/v1/object/sign/personal-photos/<owner>/<file>`; the owner's works; the bucket shows as private.
- Real devices: camera vs library pickers, HEIC uploads from iOS (the pipeline accepts what `isAllowedImage` accepts).
- Native app: no personal photo UI; with `pilotExplore` on, native first ratings still go straight to PostgREST and are
  not gated (recorded above).

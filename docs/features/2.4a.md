# 2.4a Intent filter tabs

Built 2026-11-05 under [beta-build-rules.md](../beta-build-rules.md), lane B3 (Map). Ticket: roadmap-80.md
§4, M2 "2.4a", with the founder decision that filter tabs such as "15 min away" stay on the map tab.
Needs 2.2 (merged on this lane). "Has room" depends on 4.3 and is left to 2.4b (not in this stage).

## Contract

- **Objective:** the map tab's top filters become three tabs backed by data that exists today: **When**
  (Any time / Now / Tonight / This weekend), **15 min away** (a travel limit), and **Activity** (category).
  No wall of chips. Tabs change what the map shows and never open a list. When they leave the map empty,
  say so and offer one specific expansion. Leave a slot for activity-specific tabs, shipping none.
- **Flag:** `pilotExplore`. Off: today's chip row (New, Areas, Events, every category) exactly.
- **Out of scope:** 2.4b ("Has room", "Needs players", "Beginner-friendly"); place opening hours (no data);
  real walking routes (6.1's provider is not live).

## Acceptance

1. With the flag on, the chip row is replaced by When, 15 min away and Activity tabs (New and Areas links
   stay at the end). When and Activity open a Sheet with radio choices; 15 min away is a toggle.
2. **When** filters events by overlap with the window, the same rule the discovery queries already use
   (`coalesce(ends_at, starts_at) >= endsAfter` and `starts_at < startsBefore`), in the viewer's time zone:
   Now = on now or starting within an hour; Tonight = 5 pm to 4 am (from now once it is evening; before
   4 am it is still last night); This weekend = Friday 5 pm to Monday 00:00 (from now on the weekend).
   Places have no hours, so a When tab shows events only and a line says so.
3. **15 min away** = within 1,200 m in a straight line (80 m/min walking pace) of the device location: the
   query covers the box around it and pins/rows outside the circle are dropped. Without location it
   asks; if location is off it says so and nothing changes.
4. **Activity** = one category, or any.
5. Empty map with a tab active: "No events tonight here. Try this weekend" (When widens one step: now →
   tonight → weekend → any time), else "Nothing within a 15 min walk. Show the whole map", else "No Food
   here. Any activity". One offer at a time; nothing changes until it is tapped.
6. The tabs are restorable through 2.2's URL state (`when=`, `area=15`; the area needs the location again).
7. `IntentTabs` takes an `activityTabs` slot for 2.4b; nothing is passed yet.

## Choices recorded (owner can't be asked during a run; recommended option taken)

- **Window edges** (5 pm, 4 am, Friday 5 pm to Monday) and **one hour** for Now.
- **Walking pace 80 m/min, straight line.** No routing provider is live (6.1 adapter, no key), so the tab
  is labelled "15 min away" and the doc states it is an estimate, not a route.
- **Area fits the map to the 15-minute box** when it turns on, and the query follows that box (not the
  viewport) while it is on.
- **No SQL change.** `discover_events` already takes `p_ends_after` and `p_starts_before`; the repositories
  gain an additive `endsAfter` option (and `startsBefore` on map markers), which the demo twin mirrors.
  The upcoming rule is never loosened: the cutoff is the later of "not ended an hour ago" and the window start.
- **Status chips flow under the top bar** with the flag on (tabs, notes and the 1.3 arrival bar change its
  height); the absolute position is kept when the flag is off.

## Test results

- `tests/intent-tabs.test.ts` 14/14: windows on a frozen clock (Now; Tonight at 10:00, 20:00 and 02:00;
  weekend from Wednesday, Saturday and Sunday), **across the fall-back DST change** (2026-11-01: a 12-hour
  night, weekend ending 05:00Z) and **spring-forward** (2027-03-14: a 10-hour night), and another zone; the
  overlap rule; the 15-minute box holding the circle; the widening order; the cutoff never reopening
  ended events; the real `/api/discover/events` and `/api/discover/map` routes inside a window (map
  skips places for `kind=events`, pins equal the list), an empty window, a 400 on a bad timestamp, no
  change without a window; **parity**: the demo twin and `public.discover_events` (PGlite, aligned clocks)
  return the same ids for Now, Tonight and This weekend as anonymous and signed in, and for a window
  around each upcoming event.
- **Real browser, production demo build, 390×844, port 3103** (scratch script, not committed): tabs When /
  15 min away / Activity / New / Areas; axe 0 violations; This weekend → `?when=weekend` with the
  events-only note; Now → "No events on now here. Try tonight" → tapping moved the tab to Tonight; 15 min
  away with location granted → pressed, 2 pins, `area=15` in the URL; Activity → Food with the area on →
  "Nothing within a 15 min walk. Show the whole map"; location denied → "15 min away needs your
  location, which is off."; 0 px overflow; no page errors. The first runs found two real defects, fixed
  before commit: the Sheets rendered inside the top bar's stacking context and sat under the bottom nav,
  and the events-only note covered the empty notice.
- `npm run check` with `TEST_DATABASE_URL` set (local PostgreSQL 16): **exit 0**. 83 files / 1,317 tests
  passed, none skipped, build OK.
- `npm run e2e` (demo, pilot flags on, port 3103): 18/19. The one failure, "join an event" (no
  `/events/<id>` link found on `/events`), is the same as at 2.2 and sits in lane B1's area; not touched here.

## Could not verify / limits

- "15 min away" is a straight-line estimate at walking pace, not a route; real walking time needs 6.1's
  provider with a key.
- When applies to events only until places have opening hours.
- The Supabase path was verified through the SQL function in PGlite with the same arguments the repository
  sends, not against a live Supabase project.
- No device, touch or screen-reader pass.

# 4.6 Material-change notifications

Built 2026-11-05 under [beta-build-rules.md](../beta-build-rules.md). Ticket: roadmap-80.md §4, M4 "4.6",
batch 4.6 of the approved [4.0 spec](4.0.md) (§9). Lane B1. Migration **0057** (type list).

## Contract

Time, venue, cancellation and offer events notify only affected people, deduped, respecting quiet
hours and blocks, through the existing pipeline (`notify()` → blocks, mutes, push types, dedupe;
`claim_push_batch` → quiet hours, daily cap of 5).

| Change | Recipients | Type | Dedupe |
| --- | --- | --- | --- |
| Time or venue changed | going + offered | `event_changed` | batch `event_changed:<event>` |
| Cancelled by a host | going + offered + waitlisted + interested | `event_cancelled` | `event_cancelled:<event>` |
| Cancelled below minimum (cron) | same | **new** `event_not_happening` | `event_not_happening:<event>` |
| Offer made / expired | that person | `event_offer` / `event_offer_expired` (0054) | per offer |
| Date cancelled / not happening | series followers not told above | **new** `series_update` | `series_update:<series>:<event>` |
| Series schedule changed | followers | `series_update` | `series_update:<series>:v<rule_version>` |
| Series ended | followers, once | `series_update` | `series_update:<series>:ended` |

Not material (nobody hears): title, description, capacity changes. Followers are not told about each
routine generated occurrence (D-F); interested people hear only about cancellations (D-F).

## Choices recorded (recommended option taken)

- **Service and cron changes stay silent in the trigger** (as today) and notify explicitly
  (`decide_sessions`, offers). Host RPCs that act for a backup host run as the occurrence's owner, so
  the trigger fires with that actor.
- **Ending a series** tells people going to each cancelled date (`event_cancelled`), and followers
  once ("The series has ended"), not once per date.
- **Schedule changes** tell followers once per `rule_version`; a follower who is also going to a moved
  date additionally gets that date's `event_changed` (one per affected date, batched). Recorded as a
  small overlap rather than adding exclusion logic.
- `series_update` notifications have subject type **`series`** (new value in the subject check) and
  open the series page. Both new types are pushed by default (column default + existing settings that
  push cancellations), like `event_cancelled`.
- 4.3's "not happening" notice moves from `event_cancelled` to the dedicated type; `tests/event-readiness.test.ts`
  was updated for exactly that (type only; recipients, detail and dedupe unchanged), with a comment.

## Test results

- `tests/material-change.test.ts` 9/9: non-material edits notify nobody; time change → going + offered
  only; host cancel → going, offered, waitlisted, interested once each, follower `series_update`;
  below-minimum cron → `event_not_happening` to the same audience + follower, deduped across two runs;
  schedule change → followers once; series end → followers once; **blocks** (a person who blocked the host
  hears nothing) and **mutes** apply; new types pushed by default; settings accept new types and refuse
  unknown ones; SQL type list equals the app's; demo parity on the same scenario; wording and links.
- `npm run check` with `TEST_DATABASE_URL`: exit 0 (94 files, 1,425 tests, none skipped).
- Quiet hours and the daily cap are the existing `claim_push_batch` rules (covered by
  `tests/notifications.test.ts`); new notifications enter that pipeline with `push_state = pending`.

# 6.2 — Deterministic feasibility checks

Priority: Must. Branch `codex/founder-implementation-handoff-2026-11-11`, starting commit `cb3b3d4`.
Status: **IMPLEMENTED-LOCAL.** Pure module and tests only. Not independently verified. Nothing calls it yet:
the router is 6.1 and the planner and storage are 6.3.

## Contract

- **Objective:** a pure function that decides whether a walking plan fits: given a time zone, a
  window, a start point, stops in a proposed order (fixed or flexible, with durations and optional
  opening hours), the walking legs between them, walking limits and a slack, it returns Feasible with
  times, Infeasible with the first failing constraint and one suggested edit, or Uncertain. It never
  reports Feasible on anything unknown. No I/O, no clock, no provider call.
- **Allowed files:** a shared pure module (`packages/shared/src/feasibility.ts`), the pure time-zone
  primitives it needs moved into the shared package with the app re-exporting them unchanged, a
  focused test file, this note and the ledger.
- **Prerequisites verified:** [6.0](6.0.md) spec and its 2026-11-11 validation note (6.1 and 6.2 need
  nothing from Events or Outings); Codex's review of 2026-11-12 named 6.2 as independent work that can
  proceed.
- **Out of scope:** the router, its fake and fixtures, the request memo and rate limit (6.1); the
  planner, persistence, RLS and invalidation (6.3); the editor (6.4); any provider call or key; any
  migration; non-walking or multi-city routes (X3, Later).
- **Assumptions:** legs are an input. The validator defines the `LegResult` shape from 6.0 §3 so 6.1
  can implement against it. The river and island cases are expressed here as the legs a router would
  return; the fixture-driven versions arrive with 6.1's fake.
- **Preflight:** not required. Pure code with no schema, permission, payment or privacy surface.

## Changes

- **`packages/shared/src/feasibility.ts`** (re-exported from `src/lib/trips/feasibility.ts`).
  `validate(input)` returns one of:
  - `feasible`: per stop, the arrive, start and leave times as instants and in the plan's zone, the
    walk and wait in minutes, and whether opening hours were part of the decision;
  - `infeasible`: the first failing constraint, one suggested edit (or none), and the stops reached
    before it;
  - `uncertain`: the first stop whose timing could not be decided, and why.
- **Constraints**, checked per stop in this order: stop unavailable (checked first for the whole
  plan), leg over the per-leg limit, total walking over the limit, fixed start missed, break too
  short, outside opening hours, window overrun. Defaults are 6.0's: 30 minutes a leg, 90 in all, 5
  minutes of slack.
- **Unknown stays unknown.** A leg with status `unknown`, or an "ok" leg whose seconds are not a
  clean number, stops the check there. What was decided before it stands: a failure before the first
  unknown is certain and is reported as infeasible; otherwise the answer is uncertain. It never
  returns feasible past an unknown.
- **Time.** All arithmetic is on instants. Local window times are converted with the app's
  `zonedTimeToUtc` (a skipped spring time moves forward; a repeated autumn time takes its first
  instant). A window whose end is not after its start, read as local text, ends on the next local
  day. Fixed starts are instants. The zone is required; nothing defaults to New York.
- **The suggested edit** follows the spec's order: drop the latest optional stop on the way to the
  failure, shorten the longest flexible stop by up to half, start earlier (in five-minute steps),
  swap two adjacent flexible stops. Shortening and starting earlier are offered only when re-running
  the check shows they clear the failure (`verified: true`). Dropping and swapping change the legs,
  so they are proposals that need new legs (`verified: false`). A walking failure is never answered
  with a time edit. When nothing applies the suggestion is null.
- **What may be stored** (6.0 R-2). `toStoredValidation()` reduces a result to status, the failing
  constraint's kind and stop, our suggested edit, the time and the router id. Walking minutes are
  left out because they come from the provider's durations. `storedValidationSchema` is strict at
  every level, so a value carrying any other key fails to parse.
- **Failed recalculation.** `afterRecalculation(previous, next, meta)`: when the new check could not
  be made because a leg is unknown and a verdict was saved before, the saved verdict is returned
  unchanged, with its own time, and `fresh: false`. Any real verdict replaces it.
- **Time-zone arithmetic moved, not changed.** `zonedFormatter`, `zonedParts`, `zoneOffsetMinutes`
  and `zonedTimeToUtc` now live in `packages/shared/src/timezone.ts`, and
  `src/lib/utils/timezone.ts` re-exports them. One implementation, same code, usable from the
  shared package and the mobile app. The existing 19 time-zone tests pass unchanged.

Migrations: none. Dependencies: none (zod is already in the shared package). Flags: none. No
provider, key, network call or storage.

## Choices recorded (reversible; for the reviewer)

1. **Opening hours.** 6.0 says hours are "unknown" today and that an unknown makes the result
   uncertain "for a stop whose time matters". Read literally, every plan with a place in it would be
   uncertain. So: `hours` left out means hours are not being checked, and each stop in a feasible
   result says `hours: "not_checked"` so the UI can say so; `hours: "unknown"` means the caller is
   checking hours and has none for this stop, which is uncertain; a fixed stop ignores hours because
   its start is the fact. Arriving before opening waits for the doors.
2. **Break.** The batch asks for "break constraints"; 6.0 does not define one. Implemented as
   `minBreakMin`, a pause on arrival before a stop begins, default 0 (no effect). Before a fixed
   start it must fit as well as the slack (`break_too_short`). If the founders meant something else
   (for example a rest after a long leg), this is one optional field to replace.
3. **Certain failures before an unknown are infeasible, not uncertain.** 6.0 lists "any leg unknown"
   under uncertain. A reservation already missed on known legs stays missed whatever a later leg
   turns out to be, so that is reported as infeasible. Nothing after the first unknown is judged.
4. **Malformed input throws `FeasibilityInputError`** (bad zone, unreal date, legs not matching
   stops, duplicate ids, a fixed start without an offset). That is a bug in the caller, not a verdict.

## Adversarial review

- **A leg that lies.** `{ status: "ok", seconds: NaN }` (or negative, or infinite) is treated as
  unknown rather than as a zero-minute walk.
- **Rounding.** Walking rounds up to the minute; 1,800 seconds is 30 minutes and fits, 1,801 is 31
  and does not.
- **Mutation of the input.** The check runs on a deep-frozen plan and leaves it byte-identical.
- **Clock.** Results are identical under two different frozen system times; the module reads no clock.
- **Suggestions that do not help.** An earlier fixed stop pins the evening; shortening a stop before
  it, or starting earlier, would change nothing. Those edits are tried against the plan and not
  offered; the test expects null.
- **Stored numbers.** A serialized stored verdict for a 31-minute leg does not contain "31".
- **Waiting for tomorrow.** A place open now but closing before the visit ends first came back as
  "opens too late" because tomorrow's hours fit. Found by the test, fixed: it is "closes too soon".

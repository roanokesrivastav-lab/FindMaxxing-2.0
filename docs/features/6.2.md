# 6.2 Feasibility validator

Built 2026-11-05 under [beta-build-rules.md](../beta-build-rules.md). Ticket: roadmap-80.md §4, M6 "6.2".
Design: [6.0 SPEC](6.0.md) §4, with decisions R-1 to R-6 accepted.

## Contract

- **Objective:** a pure, deterministic TypeScript validator that decides whether a proposed walking
  plan fits, in the order given, and returns `Feasible` (concrete times per stop), `Infeasible` (the
  first failing constraint plus one suggested edit) or `Uncertain` (which stop is uncertain). It never
  reports "fits" on unknowns. It is the roadmap §3 high-risk area "Itinerary feasibility".
- **Scope:** `src/lib/itinerary/` (types, validator, the stored-verdict allow-list) and its tests.
- **Out of scope:** routing (6.1), planner integration and the persisted itinerary (6.3), the editor
  (6.4), migrations, UI.
- **Required tests (roadmap 6.2 and 6.0 §4/§8), on a frozen clock:** a 6 p.m. reservation can't be
  reached at 6:20 → infeasible; a straight-line shortcut across a river; an unreachable stop →
  uncertain; provider timeout → uncertain, and the last valid saved plan is kept; overnight window; DST
  change on both transitions (first-instant rule); venue hidden after planning; a leg exactly at the
  limit; the `slackMin` boundary; an empty optional list.

## User-facing surface and flag

**None.** 6.2 is a library with no route, action, page or caller; nothing is user-reachable, so there
is nothing to put behind `pilotItinerary` yet. 6.3 wires it into the planner behind `pilotItinerary`.

## Choices recorded (owner can't be asked during a run; recommended option taken)

- **Unknown legs are a lower bound of zero minutes.** A failure found even on that bound is certain and
  is reported `infeasible` (e.g. a reservation already missed before the unknown walk starts);
  otherwise any unknown makes the plan `uncertain`. An hours check after an unknown leg is reported
  uncertain, not infeasible, because the real visit is later than the bound.
- **Hours (R-5):** places have none today. `hours` omitted means no constraint (what callers pass
  until an hours source exists); `hours: "unknown"` is how a caller says hours matter but are unknown,
  which gives `uncertain`. Known hours are local `HH:MM` ranges; a close at or before the open runs past
  midnight. The validator does not wait for opening; a visit must sit inside one range.
- **Whole minutes.** Leg seconds round **up** to whole minutes; all scheduling is on UTC instants.
- **Window.** Local `YYYY-MM-DDTHH:MM`. An end at or before the start is overnight and ends on the next
  local day (its date must be the start date). Windows longer than 26 hours (one day plus DST) are
  rejected as malformed input: the plan covers one outing day.
- **First failing constraint**, checked per stop in order: leg over max, total walk over max, fixed start
  missed (must arrive `slackMin` early; waiting is allowed), outside known hours, window overrun. A hidden
  or removed stop (`available: false`, set by the caller's visibility re-check) is checked before all of
  these and gives `stop_unavailable` with the edit "drop it".
- **One suggested edit**, in the spec's order, first that applies wins:
  1. drop the latest optional stop at or before the failing stop (`recheck: true`: legs change, the
     caller must route again);
  2. shorten the longest flexible (not fixed) stop by the least amount, at most half, that clears every
     certain failure (verified here);
  3. start earlier by the least amount, at most 180 minutes, that clears it (verified here);
  4. swap the failing stop with an adjacent flexible stop (`recheck: true`).
  Shortening and starting earlier only apply to time failures (fixed start, hours, window). If nothing
  applies, `suggestion` is `null` (e.g. a single stop more than 30 minutes away).
- **Last valid plan kept:** validation never changes a plan. `afterRevalidation()` keeps the saved
  verdict on show, marked possibly outdated, when the fresh result is uncertain because the provider
  timed out, errored or is not configured; a real answer (`no_route`, infeasible, feasible) replaces it.
- **Stored verdict (R-2):** `storedVerdict()` is an allow-list copy: status, failing code and stop,
  the suggested edit, the uncertain stop, `validated_at`, router id. It drops walk minutes, times,
  seconds and meters, so no provider duration or distance can reach 6.3's `validation` column.
- **Malformed input throws `ItineraryInputError`** (bad zone, bad local time, a fixed start without an
  offset, duplicate stop ids, leg count ≠ stop count, negative durations): a caller bug, never a verdict.

## Test results

- `tests/itinerary-validator.test.ts`: **31/31 passed.** `Date.now` is mocked to throw for the whole
  suite, which proves the validator never reads the clock (frozen-clock requirement).
  - 6 p.m. reservation reached at 6:20 → `fixed_start_missed`, 25 minutes late, with "start 25 minutes
    earlier"; after a 60-minute bar → "shorten the bar by 25"; with optional stops → "drop the bar".
  - `slackMin` boundary: arriving exactly 5 minutes early fits (waits 5); 1 second more of walking
    (rounded up to a minute) fails by 1; `slackMin: 0` arriving on the dot fits.
  - River shortcut: the same pair is feasible on the straight-line 15 minutes and infeasible on the
    28-minute detour. (6.1 adds the same case end to end through the fake router's river fixture.)
  - Unreachable stop → `uncertain` naming the island stop; still `infeasible` when the plan fails even
    with the unknown leg taken as zero.
  - Provider timeout → `uncertain`; the saved feasible verdict stays on show with
    `possiblyOutdated: true` for timeout, provider error and not configured; `no_route` and a real
    infeasible answer replace the verdict but never the plan.
  - Overnight 22:00–02:00 feasible into the next day; overrun by 10; hours that cross midnight; a midnight
    close enforced with "start 50 minutes earlier"; an overnight window across fall-back is five real
    hours.
  - DST: spring-forward night 23:00–03:00 is three real hours (overrun by 20); a 2:30 start in the gap
    becomes 3:30 EDT; fall-back 1:30 takes the first instant (EDT) while a fixed start at the second
    1:30 (EST) is not shifted; 150 real minutes fit 01:30–03:00. A non-New-York zone (Tokyo) works.
  - Venue hidden after planning: the same plan flips from feasible to `stop_unavailable`, "drop it".
  - Leg exactly 30 fits, 30:01 fails; total exactly 90 fits, 91 fails; per-outing limits override.
  - No optional stops → shorten; no stops → feasible; never reorders; hours omitted vs `"unknown"`;
    determinism; malformed input rejected; stored verdict carries no provider numbers.
- `npm run check` with `TEST_DATABASE_URL` set (local PostgreSQL 16): **exit 0**. Typecheck, lint,
  **69 files / 1,131 tests passed, none skipped**, build OK.

## What could not be verified

- Nothing calls the validator yet (6.3), so there is no end-to-end evidence from the planner, a real
  provider, or a device. Time-zone behaviour relies on the runtime's ICU data (Node here); browsers and
  native runtimes should agree but were not checked.
- Real opening hours do not exist (R-5), so the hours path is tested only with fixture ranges.

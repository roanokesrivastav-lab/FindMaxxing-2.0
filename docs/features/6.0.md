## 2. Routing provider: is "Mapbox walking" right?

**Finding: Mapbox walking is workable only if FindMaxxing never stores route results. The roadmap's
"persisted itinerary … route legs" conflicts with Mapbox's terms as currently quoted.**

| Provider | Storage of results | Cost | Notes |
| --- | --- | --- | --- |
| **Mapbox Directions (`mapbox/walking`)** | **Not allowed.** Product Terms §2.10.1 "Navigation APIs": "Customer shall not export, download, cache or store results from any request to a Navigation API". The Aug-2023 terms said "shall not cache or store results from the Directions, Isochrone, Map Matching, Matrix or Optimization APIs". The 2020 terms allowed up to 30 days. ([Product Terms Oct 2025 PDF](https://cdn.prod.website-files.com/609ed46055e27a02ffc0749b/68dddd2815cb3d82685f0096_Mapbox%20Product%20Terms%20(October%201,%202025).pdf), [Aug 2023 PDF](https://assets.website-files.com/5d4296d7a839ea49599adba1/64dcfbaf8b0b4e80b42d5c40_Mapbox%20Product%20Terms%20(August,%202023).pdf); **search excerpts**, the PDFs could not be fetched here.) A Mapbox repository PR says its public pages don't state a Directions caching rule ([mapbox-agent-skills #80](https://github.com/mapbox/mapbox-agent-skills/pull/80)), which conflicts. **Treat storage as forbidden until confirmed in writing.** | About **100,000 requests/month free, then $2.00 per 1,000** (third-party sources, e.g. [storerocket](https://storerocket.io/learn/mapbox-pricing); Mapbox's pricing page could not be fetched). | Whether results must be shown on a Mapbox map is **unverified**; the app falls back to MapLibre without a Mapbox token. |
| **Google Routes / Directions** | Google's terms restrict caching, and its policies tie results to Google maps ([Directions policies](https://developers.google.com/maps/documentation/directions/policies)). | Paid after free caps. | Same non-Google-map problem as Places (3.3 §2). Not recommended. |
| **Self-hosted GraphHopper / OSRM / Valhalla on OSM** | No provider storage restriction. OSM data is ODbL, so routes are produced works with "© OpenStreetMap contributors" attribution (3.3 §2). | No per-call cost; hosting and a monthly OSM-extract rebuild are an operations task. | GraphHopper is Apache-2.0 with a foot profile ([Geofabrik](https://www.geofabrik.de/en/data/routing.html)). OSRM (BSD-2) and Valhalla (MIT) licences are from memory, **unverified**. Profile choice matters for trails ([GraphHopper forum](https://discuss.graphhopper.com/t/graphhopper-does-not-find-obvious-route/9755)). |

**Recommendation (decision R-1): keep Mapbox walking as the tentative provider, but design so no
provider result is ever stored (§5). Keep a self-hosted GraphHopper foot profile as the named fallback** if
the owner wants stored route legs, offline robustness, or Mapbox confirms storage is forbidden and fetching
on every open is unacceptable. The adapter makes either swap a configuration change. Nothing is live in the
build: the deterministic fake is used everywhere until keys exist.

## 3. Routing adapter

```ts
interface WalkingRouter {
  id: "fake" | "mapbox-walking" | "graphhopper-foot";
  legs(points: LatLng[], opts: { signal: AbortSignal }): Promise<LegResult[]>;  // points.length - 1 legs
}
type LegResult =
  | { status: "ok"; seconds: number; meters: number }
  | { status: "unknown"; reason: "timeout" | "no_route" | "provider_error" | "not_configured" };
```

- **Walking only** (X3). The existing `drivingMinutes` output is removed from the planner tools.
- **Timeouts:** 4 s per request and 8 s per plan validation. No retries inside a request (the user can
  retry). A timeout gives `unknown`; it never throws through to "fits".
- **Caching (decision R-2):** an in-memory memo **for the duration of one server request only**, so
  identical leg requests within one validation are not repeated. Nothing is written to the database, the
  demo store, logs or a shared cache, to respect §2. The fake is cacheable (it's ours).
- **Deterministic fake** (`fake`), used for tests, demo mode, and production until keys exist:
  - walking distance = haversine × 1.3 detour factor at 80 m/min, rounded up to whole minutes;
  - a fixture **barrier** (a river polyline) turns crossing straight lines into a detour via the nearest
    fixture bridge;
  - a fixture "no route" point (island) returns `unknown`.
  - The shortcut and unreachable cases in 6.2's required tests come from these fixtures.
- **Not configured:** without the provider key the router is `fake` in demo mode and `not_configured`
  (all legs `unknown`) in Supabase mode. The UI says route times are estimates, or unavailable. Nothing
  claims a plan "fits" on unknown legs.
- **Rate and cost guard:** reuse the durable abuse limiter pattern from 0040 for route requests per user
  per hour (decision R-3: 60 validations per user per hour), so a page refresh loop can't burn quota.

## 4. Feasibility validator (pure TypeScript, no I/O)

```ts
validate(input: {
  timeZone: string;                                  // IANA; never hard-coded
  window: { startLocal: "YYYY-MM-DDTHH:MM"; endLocal: "YYYY-MM-DDTHH:MM" };   // end before start = overnight
  startPoint: LatLng;
  stops: Array<{
    id: string; point: LatLng; durationMin: number;   // time spent at the stop
    fixedStart?: string;                             // ISO instant (an event occurrence, a reservation)
    optional?: boolean;
    hours?: Array<{ opens: string; closes: string }> | "unknown";   // local HH:MM; places have none today
  }>;
  legs: LegResult[];                                 // from the router, stop order as given
  maxWalkMin: { perLeg: number; total: number };     // defaults 30 / 90 (decision R-4)
  slackMin: number;                                  // buffer before a fixed start, default 5
}) → Feasible | Infeasible | Uncertain
```

- **Order:** the AI proposes the order; the validator only decides. It never reorders silently; a
  suggested edit may propose a reorder.
- **Scheduling:** walk the stops in order from the window start. Arrival = previous departure + leg. A
  fixed stop must be reached at least `slackMin` before `fixedStart`. Waiting before a fixed start is
  allowed. Departure = max(arrival, fixedStart) + duration. Everything stays inside the window.
- **Result:**
  - `Feasible`: concrete times per stop.
  - `Infeasible`: the **first failing constraint** (fixed start missed, window overrun, leg over max,
    total walk over max, outside known hours) plus **one suggested edit**, chosen deterministically in
    this order: drop the latest optional stop, shorten the longest flexible stop by up to half, start
    earlier, then swap two adjacent flexible stops.
  - `Uncertain`: any leg `unknown`, or hours `unknown` for a stop whose time matters. It **never** reports
    feasible on unknowns; it says which stop is uncertain.
- **Time and DST:** local wall times convert to instants with the app's `zonedTimeToUtc`. A spring-gap
  time moves forward; a repeated fall-back time takes the **first** instant, matching 4.0 decision D-G.
  An overnight window (end ≤ start locally) ends on the next local day. All arithmetic is on instants.
  Fixed starts come from the anchored occurrence (4.0) as instants, so a DST change between plan and
  event can't shift them.
- **Hidden venue:** the caller re-checks every stop's visibility for the requesting member before
  validating. A stop that became hidden or removed makes the result `Infeasible` with
  `stop_unavailable` and the suggested edit "drop it".
- **6.2 required cases:**
  - a 6 p.m. reservation can't be reached at 6:20 → infeasible;
  - a straight-line shortcut across the river → the detour makes it infeasible;
  - an unreachable stop → uncertain;
  - provider timeout → uncertain, and the last valid saved plan is kept;
  - overnight window;
  - DST change on both transitions;
  - venue hidden after planning.
  - Also: leg exactly at the limit, `slackMin` boundary, an empty optional list.

## 5. Persisted, versioned itinerary (owned by the outing)

M5 is in scope after events (owner position), so the itinerary belongs to an outing (5.0). Solo "Plan my
day" keeps today's save-as-list behaviour.

`outing_itineraries`:
- `id`, `outing_id`, `version` (unique per outing), `created_by`, `created_at`, `is_current`;
- `time_zone`, `window_start_local`, `window_end_local`, `start_point`;
- `anchor_event_id` (the occurrence from 5.5; nullable);
- `stops jsonb`: our plan only, i.e. stop id/kind, the planned local arrive/leave chosen by the planner,
  `duration_min`, `optional`, `fixed`;
- `validation jsonb`: `{ status, failing?, suggestion?, validated_at, router }`. This is our verdict and
  our planned times, with **no provider durations, distances or geometry** (decision R-2);
- `invalidated_at`, `invalidated_reason` (`anchor_moved`, `anchor_cancelled`, `stop_unavailable`).

Rules:
- **Every save is a new version.** An append-only trigger blocks updates except `is_current` and the
  invalidation columns.
- **Readable by current outing members only** (RLS via 5.0's membership function). A removed member loses
  access at once, on the page and through the API. Writes go only through RPCs (`save_itinerary_version`)
  that check membership and the outing's lock state (5.0).
- **Route legs are not stored.** Opening an itinerary re-requests legs and re-validates, which shows
  "checked just now". If the router is unavailable, the stored verdict is shown with its `validated_at`
  and marked possibly outdated.
- **Anchor changes:** 4.0's material-change path (time or venue change, cancellation of an occurrence)
  sets `invalidated_at` on current itineraries anchored to it, in the same transaction, and notifies outing
  members (5.0 notifications). "Moving or cancelling the game invalidates the plan" (6.3 acceptance).

## 6. Planner changes (6.3)

- **Zone:** the outing's zone, else the anchor occurrence's `time_zone` (4.0), else the viewer's zone
  cookie, else `DEFAULT_TIME_ZONE`. The hard-coded zone at `planner.ts:82` is removed.
- **The AI proposes order and durations only.** `submit_plan` drops `travel_minutes`, and
  `arrive`/`leave` become proposals. The server calls the router and the validator, and the user sees the
  validator's times. When infeasible, the server may ask the model once more with the failing constraint;
  otherwise it shows the suggestion.
- The `distance` tool returns the router's walking minutes (fake by default), never driving.
- Tests keep stubbing the model (as `tests/trips.test.ts` does) and use the fake router, so they make no
  real calls.

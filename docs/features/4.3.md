# 4.3 Minimum attendance and readiness

Built 2026-11-10 under [beta-build-rules.md](../beta-build-rules.md), from the approved spec
[4.0.md](4.0.md) §5, §9 and §16. Branch `events-4.0`, migration `0051`.

## Contract

- **Objective:** a host can set a minimum attendance, a decision deadline and whether the venue is
  confirmed. Cards show the Readiness row. At the deadline a cron cancels sessions below the minimum and
  tells the people going; a host confirm blocks that.
- **Out of scope:** waitlist and offers (4.4), series templates (4.5a), Party poster (4.8), native UI.
- **Required tests:** frozen clock around the deadline (before, at, after, host confirm); the Readiness
  row with missing fields says nothing false.

## Changes

- **Migration `0051_session_rules_and_readiness.sql`**
  - `events.min_attendance`, `decision_deadline`, `venue_status`, `decision`, `cancel_reason`. None is in
    the column-level `UPDATE` grant, so clients cannot write them directly. Events already cancelled are
    marked `cancel_reason = 'host'`.
  - `guard_event_session_rules()` (trigger): the one place the rules' shape is checked, whoever writes
    the row. A signed-in creator can never supply `decision` or `cancel_reason`. A host cancel records
    `cancel_reason = 'host'`. Moving the start carries the deadline at the same lead time.
  - `findmaxxing_private.seats_taken()`: the single capacity definition. Here it is going + live paid
    holds, "live" against `clock_timestamp()`. 4.4 adds live offers to this same function.
  - `events_readiness(uuid[])` and `event_readiness(uuid)`: the Readiness numbers for events the caller
    can see (`can_view_event`), callable by anon.
  - `set_session_rules()`, `confirm_session()`: host only, active account, event row lock first.
  - `decide_sessions(p_now)`: service role only. Each event is decided under its row lock, in id order.
    Below the minimum: `cancelled` / `below_minimum` / `not_happening`, and each person going gets
    `event_not_happening` with a null actor and dedupe key `event_not_happening:<event>`.
  - New notification type `event_not_happening` in the type check, `check_notification_settings` and
    the push default. Existing settings rows that push `event_cancelled` get it added.
  - `create_event_with_details` and `update_event_with_tags` take a defaulted `p_session_rules`, so an
    event and its rules are one transaction.
- **Shared:** `packages/shared/src/readiness.ts` (`readinessParts`, `readinessText`,
  `formatConfirmBy`); `EventReadiness`, `SessionRules` and the new event fields in `types.ts`.
- **Repositories:** `events.setSessionRules`, `confirmSession`, `decideSessions`; lists and `get`
  attach `readiness`. Demo twin in `src/lib/data/demo/sessions.ts`. Demo store version 17.
- **Cron:** `/api/cron/notifications` (every 15 minutes) decides sessions before sending reminders.
- **Web, behind `pilotEvents`:** minimum, "decide by" and venue fields in the event form; the event
  card shows the Readiness row and drops the calendar date block (founder decision); the event page
  shows the row and a host "Confirm it's on" button.

Dependencies added: **none**.

## Decisions taken (gaps in the spec)

- **`seats_taken` arrives here, not in 4.4.** The Readiness row needs "spots open" now. It is one
  function that 4.4 extends, so there is still one definition.
- **`event_not_happening` arrives here, not in 4.6.** The spec lists new types under 4.6 but 4.3 must
  send this one. Each new type is added by the ticket that first sends it; 4.6 keeps the recipient and
  follower rules.
- **A deadline needs a minimum**, and a person cannot set a deadline that has already passed (the next
  cron run would cancel the event at once).
- **Who counts as going:** `count(event_attendees)`, which includes the host.
- **Readiness wording:** "It's on" once decided; nothing about the deadline after it has passed; the
  deadline is worded in the event's zone and names that zone when the viewer's clock differs ("4 p.m.
  EST"), because the rest of the card is still in the viewer's zone until 4.1.
- **Cron placement:** the existing 15-minute notifications cron, so a decision is at most 15 minutes
  late.
- An ended event is never decided: the existing owner guard refuses any update to it.

- `tests/session-rules.test.ts` (new): **37/37 passed.** PGlite: defaults; rules on create; six refused
  shapes leave no event; outcome columns not client-writable (insert and update); `set_session_rules`
  as host, other user, anon, suspended, cancelled; keep/replace/carry on update; readiness numbers
  including a live and an expired paid hold; visibility of `events_readiness`; the deadline just

  person on a re-run; muted type; paid tickets go to `refund_pending`; service role only. Readiness

# 4.3 Minimum attendance and readiness

Built 2026-11-05 under [beta-build-rules.md](../beta-build-rules.md). Ticket: roadmap-80.md §4, M4 "4.3",
batch 4.3 of the approved [4.0 spec](4.0.md) (§5, §16). Lane B1. Flag: `pilotEvents`. Migration **0052**.

## Contract

- `events.min_attendance`, `decision_deadline`, `venue_status`, plus `decision` (open / happening /
  not_happening) and `cancel_reason` (host / below_minimum / series_ended) from the 4.0 spec.
- **Readiness row**: the default event card wherever events show as cards (`EventCard`, so lists,
  place "Happening here", explore preview, rails) and in the Events tab rows and the event page. It reads
  "8 going · 4 spots open · 2 more needed · host confirms by 4 p.m.", each number from its own field,
  computed by one function, `event_readiness()` (SQL), mirrored by `computeReadiness` (TS, demo).
- **Cron**: at the deadline, an open session below its minimum becomes `cancelled` /
  `below_minimum` / `not_happening` and everyone going is notified explicitly; one at or above becomes
  `happening`. The host can confirm earlier (`confirm_session`), which blocks the auto-cancel.
- **Off**: events carry no readiness, so every card is today's card (with its date tile); no form
  section; the cron step does not run.
- No calendar date block in any new card (founder decision). Party poster is 4.8.

## Choices recorded (recommended option taken)

- **Readiness delivery:** a PostgREST computed column (`readiness:event_readiness` on every event
  select) added only when `pilotEvents` is on, so flag-off queries are byte-for-byte today's.
  `event_readiness(uuid)` also exists for native (8.1b). Both return null for an event the caller cannot
  see; counts only, never names.
- **Spots open = capacity − going − live paid holds** (spec §6.2's `seats_taken`; 4.4 adds live offers).
  Held seats are never "open". A field that is not set says nothing: no capacity → no spots part; no
  minimum → no "more needed"; met minimum → "Minimum met"; no deadline → no "host confirms by".
- **Deadline input** is a lead time ("4 hours before the start", from fixed options), stored as an
  absolute `decision_deadline` so the cron compares instants (DST-safe). A deadline needs a minimum
  (otherwise there is nothing to decide); the form says so.
- **Notification type:** 4.3 uses the existing `event_cancelled` type with detail "Not enough people
  signed up" and dedupe key `event_not_happening:<event>`. 4.6 introduces the dedicated
  `event_not_happening` type (spec §9).
- **Cron placement:** the decision runs inside `runNotificationJobs` (the existing 15-minute
  notifications cron), before reminders and pushes, so the notices go out in the same run. Placing it
  in the route itself would have changed the route's config dependency, which the existing cron
  authorization test mocks.
- **Supabase update ordering:** an edit may move the start before the old deadline, or capacity
  below the old minimum. The repository clears those two fields first, runs the existing update RPC,
  then writes the new values (each step valid; a failure leaves no deadline, so no auto-cancel).
- **Confirm button** shows for the creator only, while the decision is open and a minimum is set.
- Demo seed: "Thursday pickup basketball" (min 8, decide 4 h before) and "3v3 basketball run" (min 6,
  2 h before), in SQL seed and demo store alike.

## Test results

- `tests/event-readiness.test.ts` 16/16:
  - row text: the ticket's exact sentence; each missing field omitted; held seats not open; met /
    confirmed / not happening / waitlist / venue / cancelled; deadline in the event's zone with day.
  - PGlite: constraints (min 2..capacity, deadline ≤ start, venue values); only the owner sets the rules
    (**another user, moderator, anon** change nothing); `decision`/`cancel_reason` have no grant;
    `event_readiness` equals the TS mirror including a live vs an expired paid hold; null when hidden.
  - `confirm_session`: other user, moderator refused; anon has no execute; after the deadline refused.
  - **frozen clock** around the deadline: 1 ms before → untouched; at → not happening, the two people
    going each get exactly one notice (re-run adds none), a paid ticket moves to `refund_pending`;
    at/above minimum → happening; host-confirmed → untouched; no minimum → happening;
    `decide_sessions` refused for authenticated and anon.
  - demo parity (numbers, rule checks without partial writes, decide, dedupe, confirm blocks cancel);
    the **real cron job** (`runNotificationJobs`) decides only with `pilotEvents` on; flag off → no
    readiness; the card (no date tile; price, Full, Cancelled visible); the page (row; host-only confirm).
- `npm run check` with `TEST_DATABASE_URL`: exit 0 (80 files, 1,287 tests, none skipped). The first
  run had two failures: `cron-auth.test.ts` (fixed by moving the cron step, see above) and
  `auth-limits.test.ts` "attempt 6 … rate-limited", a wall-clock window-boundary flake in another
  area ("Try again in a minute" vs "in N minutes"); it passed on the re-run with no change.
- Browser (production demo build, 390×844, 100%/200%): Events tab (13 Readiness rows), the event page
  as the host (row + confirm), a place page's "Happening here" card, the create form. No page errors,
  axe 0 violations, 0 px overflow except the pre-existing 25 px on the create form at 200% (see 4.1).

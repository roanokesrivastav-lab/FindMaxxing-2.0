## Events 4.0 Amendment A1

**Approved with required changes.** The founder decision to build recurring events with going-only attendees and defer waitlists is sound. The following changes must appear in the revised brief before dependent code starts.

- **Make capacity enforcement apply to every admission path.** Reject a blanket paid-ticket exemption. A paid ticket can outlive an attendee row when a buyer leaves and the seat is resold. An old paid ticket grants eligibility to attempt re-entry. It does not hold a seat after leaving. A fulfillment insert can use the regular capacity check after the service converts its own live hold to paid in the same transaction under the event lock. At that point `seats_taken` counts the other going attendees and live holds. Keep the host’s existing ticket exemption and enforce capacity for the host as well. A late, cancelled or otherwise unfulfillable confirmation follows the existing refund-pending contract. The current capacity-lowering gap can strand a paying customer or trigger a refund. It is not evidence that the current trigger already seats beyond capacity, because the existing trigger rejects an insert when the going count is full.
- **Specify the actual lock order and expiry boundary.** `confirm_ticket` currently locks the ticket first in [0028](../../supabase/migrations/0028_payment_event_processing.sql), then acquires the event lock via the attendee trigger. `reserve_ticket` and cancellation already take the event before updating ticket rows in [0022](../../supabase/migrations/0022_payments.sql). Identify the event, acquire its lock, then lock and re-read the ticket before deciding if the hold is live. Use a consistent time check under lock for fulfillment and seat accounting. Audit cancellation, reservation, refund, expiry and account deletion for reverse lock order. Keep existing outcome and notification semantics. Review access to the private seat-count helper from the capacity guard under the actual database roles. `seats_taken` is intentionally revoked from API roles in [0051](../../supabase/migrations/0051_session_rules_and_readiness.sql), so an invoker guard cannot call it blindly.
- **Keep legacy direct inserts and deletes.** The existing web and native clients can keep using them with database capacity and authorization enforcement. Defer typed wrappers unless a specific client contract needs them. A wrapper must enforce the same access as a direct write. No grant change is needed for this amendment.
- **Move committed occurrences in place.** Preserve the IDs of occurrences with attendees, tickets, chat history or an outing anchor. The current attendance trigger creates a conversation on the first RSVP. The series brief must say how host-only generated occurrences are classified and prove that its rule does not delete chat history or recreate cancelled dates. Define conflict handling when rescheduling collides with another occurrence’s local date.
- **Specify one notification path per change.** Name how authenticated writes and service/cron writes avoid double delivery, and how two successive legitimate edits can each reach the recipient. A null actor bypasses the actor-block check inside `notify()`. Check current event or series access and relevant block relationships before generating content for each recipient. Cover revoked visibility and overlapping attendee/follower recipients. Host-recorded attendance may support series history. R4’s explicit self-report requirement remains a separate contract and cannot be satisfied by a host mark alone.

**Implementation handoff.** Scope the new migration(s) to capacity, series and material-change functions and triggers, their repository/demo paths, and the matching tests. Preserve the staged waitlist snapshot, reserved migration 0052, payment grants, existing client permissions and founder priorities. Use real two-connection PostgreSQL for the races already listed in A1. Add paid leave → seat reallocated → old ticket re-entry, fulfillment versus cancellation, and fulfillment at expiry versus a new reservation. Assert capacity, correct payment disposition, lock order, and valid results for authenticated and service callers. Use controlled interleaving and verify that the race tests detect removal of their relevant guard. Cover repeated edits, retry dedupe, role/visibility checks, and demo parity. Resolve the hosted 0052 history before any hosted rollout.

## Outings 5.0 Amendment A1

**Approved with required changes.** Keep the gate after the verified Must Events subset and exclude 4.4 from it. Keep all §8 and §11 role, privacy and concurrency requirements. The anchor lifecycle needs an explicit joint contract with 4.5a before 5.5 is implemented.

- **Give anchor creation and series regeneration the same occurrence lock.** Under the event lock, recheck visibility, status and the caller’s current going row before creating the outing. Serialize against a direct leave as well as joins and edits, for example by locking the attendee row after the event. Regeneration must lock each candidate in a deterministic order and check for an anchor after taking that lock, before deletion. Document the cross-table order for all paths that touch events, outings and itinerary versions. Avoid a path that locks an outing and then waits for the event while the material-change trigger holds the event and waits for the outing.
- **Define the database behavior for every deletion path.** Use a foreign key with an explicit lifecycle that prevents orphaned or silently detached plans. In addition to regeneration, specify the handling of owner deletion, moderation, and account deletion when an anchor already exists. Preserve required account deletion and privacy guarantees. An anchor flag and any applicable itinerary invalidation must be atomic with the material change and must not carry private event details to members who cannot read them. Where a later migration introduces the itinerary table, document which invariant is enforced by each ticket.
- **Keep hard vetoes under the outing lock.** The 5.3 brief must say how standing constraints relate to item vetoes and must apply eligibility and veto checks to both manual and deadline locks. Cover direct constraint changes racing either lock path so a previously vetoed or newly invalid item cannot be selected by a concurrent write.

**Implementation handoff.** Scope 5.1–5.4 to the existing outing tables, RPCs, membership, invites, shortlist, vote/lock and views as specified. Scope the event integration to 5.5 and coordinate its schema/trigger with 4.5a. Keep participant and outing membership separate. Preserve existing privacy, refund, client and scheduling contracts. Add two-connection proofs for regeneration versus anchor creation, direct leave versus anchor creation, and constraint edits versus manual/deadline locks. Test event deletion and account deletion with an existing anchor, unauthorized/removed-member access through the actual API, and event-change invalidation with and without an itinerary. Record an explicit outcome for each ordering and verify that neither path leaks an event or private save through the outing log or a notification.

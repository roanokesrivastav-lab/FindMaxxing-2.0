# 4.4 Waitlist and offers

Built 2026-11-05 under [beta-build-rules.md](../beta-build-rules.md). Ticket: roadmap-80.md §4, M4 "4.4",
batch 4.4 of the approved [4.0 spec](4.0.md) (§6, §7, §11, §13, §14, §15). Lane B1. Migration **0054**.
Roadmap §3 high-risk area ("seat claims, waitlist offers"; "legacy write paths"): **the two-connection
PostgreSQL race tests ran on real PostgreSQL 16 and passed** (below). Status: **VERIFIED** for the gate.

## Contract

- `event_participants` (interested / waitlisted / offered / declined / left), `event_attendees` still
  meaning exactly "going" (D-B). `seats_taken = going + live offers + live pending paid holds`, compared
  against `clock_timestamp()`.
- Atomic definer RPCs: `join_event`, `leave_event`, `set_interest`, `accept_offer`, `decline_offer`,
  `host_remove_participant`; internal `offer_next`; service `expire_offers` (15-minute notifications
  cron). Every seat-changing path locks the event row first.
- Offer window 2 h, capped to 30 min before the start; no offers inside the cutoff (D-D). Ineligible
  people (suspended, closing, can't see the event) are skipped but keep their place (D-M).
- **Legacy writes closed exactly as §13 says:** phase 1 (new `check_event_join` on `seats_taken`, which
  also passes open seats to the queue first, so a direct insert cannot jump it; after-delete trigger
  `offer_next`) and **phase 2 in the same release (D-I accepted: no native build has shipped)**: API users
  can no longer insert or delete `event_attendees` directly.
- Capacity can't drop below going + live offers; raising it offers seats; cancelling ends live offers.
  The price locks while anyone is waitlisted or offered.
- **Paid events: nothing new** (D-L). No waitlist; `join_event` on a priced event says
  `payments:ticket_required` (a paid ticket holder still gets in, as with the old trigger);
  `offer_next` is a no-op on priced events; `reserve_ticket`, `confirm_ticket`, `mark_ticket_refunded`
  are unchanged. 4.0's paid race case 7 passes.
- Web repository switched to the RPCs (demo twin at parity). Notifications for "offer made" and "offer
  expired" (§9) with dedupe keys. Event page (pilotEvents): Join / Join waitlist / Interested / Leave
  waitlist / Accept spot / Decline, Waitlisted / Interested / offered status labels, and the host's
  waitlist with names (D-K: names to hosts only; everyone else sees the count in the Readiness row).

## Choices recorded (recommended option taken)

- **Phase 2 policy detail:** the insert policy is replaced by "creators attend their own events"
  (`user_id = auth.uid()` and the caller created the event), because `create_event_with_details` runs
  as the caller (0036) and inserts the creator's attendance. The delete policy is dropped. The trigger
  still applies to that insert.
- **Native:** `apps/mobile/lib/api.ts` join/leave (`:76/:79`) now call `join_event` / `leave_event`, so the
  never-shipped native app does not break under phase 2. This is a two-call data change, not UI; the
  native waitlist/offer UI stays in 8.1b (a native join on a full event now returns "waitlisted" and the
  screen does not show it yet).
- **Notification types:** `event_offer` and `event_offer_expired` are added here (the offers themselves
  are built here and case 10 needs them); 4.6 adds `event_not_happening` and `series_update`. Both new
  types are pushed by default (added to the column default and to existing settings that push
  cancellations).
- **Dedupe keys** are `event_offer:<event>:<offered_at ms>` / `event_offer_expired:<event>:<offered_at ms>`,
  not the spec's `…:<user>:<offered_at>`: the key is already unique per person (the unique index is
  `(user_id, dedupe_key)`), and the user id pushed it past the 100-character `dedupe_key` limit.
- **`can_view_event_as`** (internal) answers visibility for a waitlisted person at offer time by
  temporarily setting `request.jwt.claim.sub`, so the existing `can_view_event`/`can_view_place` rules
  are reused instead of copied.
- **Removing capacity** (host sets unlimited): everyone still waiting is offered a seat.
- **Expiry sweep runs whatever the flag** (waitlists are data); the cancel-below-minimum step (4.3)
  stays behind `pilotEvents`.
- **Demo store:** participants live in an optional collection created on first use, so the persisted
  demo file needs no version bump (avoids a cross-lane `STATE_VERSION` collision).
- `reserve_ticket` was **not** redefined to use `seats_taken`: offers cannot exist on a priced event
  (price lock + `offer_next` no-op), so its count is already identical, and the paid path stays
  byte-for-byte as it was.

## Changed existing tests (behaviour deliberately changed; none weakened or skipped)

the RPCs instead of direct inserts/deletes; what each asserts is unchanged:
`tests/messaging.test.ts` (group chat follows attendance; fellow attendee may message),
`tests/interaction-attribution.test.ts` (join/leave logged), `tests/notifications.test.ts` (join
notifications, SQL/demo parity), `tests/payments.test.ts` (a ticket holder can leave and come back; now
also asserts the RPC answers "going"). `tests/demo-repository.test.ts`: joining a **full free event** now
waitlists instead of throwing "full" (the 4.4 rule), so the assertion changed from "rejects /full/" to
"returns waitlisted, attendee count unchanged". `tests/fixtures/function-grants.ts`: six reviewed
allowlist entries.

## Test results

**HARD GATE: `tests/event-waitlist-pg.test.ts` on real PostgreSQL 16 (`TEST_DATABASE_URL` set, two
independent connections via `tests/helpers/postgres.ts`): 10/10 passed, none skipped.** Output:

```
[race] case 1: 20 rounds, winner per round aaaaabaaaaaaaaaaaaab (exactly one going each time)
[race] case 2: 10 rounds trigger path → full ×10; API direct insert → RLS refusal; offer holder going every time
[race] case 3: 16 rounds at the expiry instant → going 7, expired-and-passed-on 9; never both, never neither
[race] case 4: 10 rounds of double accept → one going row each, the second call a no-op
[race] case 5: 12 rounds → the waitlisted person got the offer, the newcomer was waitlisted every time
[race] case 6: 12 rounds → capacity lowered first 3 (join waitlisted), join first 9 (lowering refused); invariant held
[race] case 7: 8 rounds → one reservation wins, the other 'This event is full'; confirm_ticket inserts the going row; no waitlist on paid events
[race] case 9: 10 rounds → cancel first 5 (join refused), join first 5; no offers survive; nothing joins afterwards
[race] case 10: offer_next ×2 concurrently → 1 offer, 1 notice; expire_offers ×2 concurrently → 1 expiry notice, 1 next offer
[race] case 11: 1000 calls over 2 connections, 0 errors; final going 5/5 (varies by run); going+offers ≤ capacity, nobody both going and participating, offers ahead of the queue
```

Case 8 (concurrent series generation) belongs to 4.5a. One development run of case 11 failed with
"6 ≤ 5": the invariant check read capacity, going and offers in three separate statements while the
other connection kept writing, so it compared two snapshots. The check now reads every count in one
statement (one snapshot); three consecutive re-runs plus the full `npm run check` passed. No SQL changed
for that fix.

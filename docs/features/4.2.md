# 4.2 Structured activity details and `events.time_zone`

Built 2026-11-10 under [beta-build-rules.md](../beta-build-rules.md), from the approved spec
[4.0.md](4.0.md) §4 and §16. Branch `events-4.0`, migration `0050`.

## Contract

- **Objective:** an event can carry a few structured facts about the activity (run, volleyball,
  basketball, pickleball, walk), shown in plain language; every event has an IANA time zone.
- **Out of scope:** the event page reorder (4.1), the Readiness row (4.3), series templates (4.5a),
  native UI (8.1b).
- **Required tests:** validation of each kind, plain-language rendering that says nothing false for
  missing fields, no numeric skill rating, RLS and ownership on the new columns, demo parity.

## Changes

- **Migration `0050_event_activity_and_time_zone.sql`**
  - `events.time_zone text not null default 'America/New_York'`. Existing rows take the default, which
    is what the app assumed for every event before. `valid_time_zone()` accepts `UTC` or an
    `Area/Location` name the server knows; a trigger refuses anything else (`events:bad_time_zone`).
  - `events.activity_details jsonb`, with a check: an object, a known `kind`, scalar values only, at
    most 600 characters.
  - `create_event_with_details` and `update_event_with_tags` are dropped and recreated with two extra
    parameters that have defaults (`p_time_zone`, `p_activity_details`), so callers that send only the
    old named parameters (the native app) still resolve. On update, null keeps the stored value and an
    empty object clears the details.
  - Neither column is in the column-level `UPDATE` grant, so they change only through the function.
- **Shared** `packages/shared/src/activity.ts` (export `@findmaxxing/shared/activity`): the exact
  shape per kind (zod), `describeActivity()` and `activitySummary()` for wording, and
  `activityFromFields()` for the form. `Event` gains `timeZone` and `activityDetails`.
- **Repositories:** both map and write the two fields. `src/lib/data/events.ts` holds the
  `events:<key>` error wording shared by SQL and the demo twin. The Supabase adapter checks the exact
  shape before calling the function, so both sides refuse the same input.
- **Web, behind `pilotEvents`:** an Activity section in the event form that shows only the fields for
  the chosen kind; the event page lists the details; event cards show a one-line summary. The form
  always sends the zone the times were typed in (not flag-gated: it is data every later ticket needs).
- `PilotFlagsProvider` (root layout) hands server-resolved pilot flags to client components such as
  `EventCard`, which is rendered from six places.
- **Seed:** "Thursday pickup basketball" has activity details in both the SQL seed and the demo store.
- `.claude/launch.json`: a `web-demo-pilot` preview configuration that sets `NEXT_PUBLIC_FEATURES`
  itself (see "Could not verify").
- `apps/mobile/lib/api.ts`: `toEvent` fills the new required `timeZone` so the app still compiles.

Dependencies added: **none**.

## Decisions taken (gaps in the spec)

- **Where an event's zone comes from.** The spec adds the column but does not say how a new event gets
  its value. The form sends the zone the host typed the times in (the browser's zone). There is no
  place-to-zone lookup in the app and adding one would need a dependency. Editing an event keeps its
  zone.
- **Units.** Distances are miles and pace is minutes per mile (the pilot city is Columbus).
- **Skill is a description.** Pickleball "level" is one of four plain phrases; nothing accepts a number.
- **Unticked boxes are not stored.** "Beginners welcome" unticked stores nothing, so the page never
  claims the opposite.
- **Database check is structural, the app's is exact.** SQL checks kind, scalars and size; the exact
  fields per kind live in one place (`activity.ts`) and both repositories apply them.

## Test results

- `tests/event-activity.test.ts` (new): **35/35 passed.** PGlite: backfill, old 12-parameter call, zone
  accepted/refused (including POSIX-style `ABC+3` and legacy `EST5EDT`), details refused (unknown
  kind, no kind, nested value, list, oversized), keep/clear/replace on update, owner only, direct
  column update denied, anon can read. Shape and wording tests. Demo twin behaves the same.
- The "no kind" case **failed on the first run**: the check evaluated to NULL and a CHECK passes on
  NULL. Fixed in the migration (`coalesce(…, false)`, and a `CASE` so `jsonb_each` never sees a
  non-object).
- `npm run check` with `TEST_DATABASE_URL` set (throwaway local PostgreSQL 17.11): **exit 0**.
  Typecheck, lint, **69 files / 1,135 tests passed, none skipped**, build OK. Mobile `tsc --noEmit`: exit 0.
- One earlier run of the check failed in `tests/auth-limits.test.ts`, which is unrelated: its assertion
  did not allow the limiter's "in a minute" wording, so it failed when run in the last minute before a
  quarter-hour. Fixed in its own commit (`dbf4e2d`), as the preflight allows for a trivial unrelated
  failure.
- Browser, demo mode with `pilot` on: the Activity section appears, switching kind swaps the fields,
  the seeded event's details prefill on edit, saving a changed player limit shows on the event page,
  and the events list card shows "Basketball · 4 v 4 · Up to 10 players". No console errors.

## Could not verify / limits

- **NOT VERIFIED: hosted Supabase.** Nothing was applied to staging. In particular, that PostgREST
  resolves the recreated functions for a caller sending only the old named parameters was tested
  against PGlite by positional call, not through PostgREST.
- **NOT VERIFIED: native app at runtime.** It compiles; it was not run.
- The preflight's local PostgreSQL on port 5432 needed a password that is not in the repository, so
  the real-database runs used a throwaway cluster started for this work (port 54329, PostgreSQL 17.11;
  the spec's DST check was made on 16).
- `.env.local` on this machine sets `NEXT_PUBLIC_FEATURES` without `pilot`, which overrides
  `.env.development`, so `next dev` here shows no pilot features. I did not edit it; the new preview
  configuration sets the variable itself.
- A browser that reports a legacy zone name (`GMT`, `EST5EDT`) creates the event in
  `America/New_York`, because the database only accepts `UTC` or `Area/Location` names.

# 4.2 Structured activity details

Built 2026-11-05 under [beta-build-rules.md](../beta-build-rules.md). Ticket: roadmap-80.md §4, M4 "4.2",
batch 4.2 of the approved [4.0 spec](4.0.md) §16. Lane B1. Flag: `pilotEvents`. Migration **0051**.

## Contract

- Shared types and validation in `packages/shared` for activity details per kind: **run** (distance,
  pace range, regroup, no-drop explained), **volleyball / basketball** (format, player limit, beginners
  welcome), **pickleball** (level, singles/doubles, paddles available), **walk** (one optional note).
- EventForm shows only the chosen kind's small section; the event page (Requirements) and the Events
  tab's expanded row render them in plain language. Skill is a plain description, never a number.
- Per 4.0 §16, this batch also adds **`events.time_zone`**, backfilled to `America/New_York` (today's
  app-wide default) and required afterwards. The event page now shows times in the event's own zone,
  labelled.
- Off (`pilotEvents` off): no form section, the action ignores the inputs, the legacy page is unchanged.

## Choices recorded (recommended option taken)

- **Storage:** `events.activity_details jsonb`, checked in SQL by `valid_activity_details` (kind list,
  per-kind key whitelist, types, ranges, the skill list, pace format), mirrored by
  `activityDetailsSchema` (the stricter of the two: it also checks the faster pace comes first) and by
  the demo store. Written through a column grant, like 4.1, so RLS and the owner guard still apply.
- **Skill levels** are four plain sentences ("New to it: we'll show you the basics", "Casual: you know
  the rules", "Regular: you play most weeks", "Competitive: games are intense"). A test asserts none
  contains a digit, and SQL refuses a numeric level.
- **Units:** run distance in miles by default (US pilot), km selectable; pace is per the same unit.
- **Time zone validation** uses a trigger (`at time zone` must not raise), the same way
  `notification_settings.time_zone` is checked. The form stamps the planner's browser zone (the zone
  the date and time were typed in), only with `pilotEvents` on.
- **Where the zone shows:** event page in the event's zone. List rows (the 1.5 tab) stay in the
  viewer's zone, since they are compared against each other and against "Today".
- **Demo seed:** three seed events carry details ("3v3 basketball run", "Thursday run club",
  "Thursday pickup basketball", the last also with a newcomer block), written identically to the SQL
  seed and the demo store.

## Test results

- `tests/event-activity-details.test.ts` 10/10: per-kind schema, numeric skill refused, paces, plain
  lines show only filled fields; PGlite backfill (every existing event `America/New_York`), seeded
  details present, owner sets details and zone, **another user, moderator and anon** change nothing,
  SQL refuses unknown zones / foreign keys / numeric skill / bad pace / fractional player limit /
  unknown kind; demo parity; form parser (only the chosen kind, errors by input name, None clears);
  **real create action** stores details and zone; **real page** shows Requirements and the Berlin time
  in Berlin's zone.
- `npm run check` with `TEST_DATABASE_URL`: exit 0 (77 files, 1,251 tests, none skipped).
- Browser (production demo build, 390×844, 100% and 200%): event page with details + first-time block,
  the create form with the run section open, the Events tab expanded row. No page errors, axe 0
  violations, 0 px overflow, except the create form at 200%, which overflows 25 px from the existing
  date/start/end three-column grid (pre-existing, recorded in 4.1, unchanged).

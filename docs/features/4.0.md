## 2. Model overview

```
event_series ──< event_series_hosts           (owner, backup hosts)
     │       ──< event_series_followers       (follow = updates only, never RSVP)
     │
     └──< events  (= occurrences; series_id null for a one-off event)
              ──< event_attendees              (GOING only — unchanged meaning)
              ──< event_participants           (interested / waitlisted / offered / declined / left)
              ──< tickets                      (paid fulfillment — unchanged)
```

**Decision D-A (recommended): an occurrence is a row in `events`.** Every existing feature (discovery,
cards, detail page, reminders, chat, tickets, refunds, reports, moderation, `can_view_event`, account
deletion) already keys on `events.id`. So:

- an existing event **is** an occurrence with `series_id = null`: no data migration, no id changes;
- occurrence ids are stable once created, which anything that later anchors to an occurrence
  (see §12, outings) can rely on.

**Decision D-B (recommended): `event_attendees` keeps meaning exactly "going".** Non-going states live in
a new `event_participants` table. Every legacy read, count and trigger (chat, reminders, interactions,
`attendee_count:event_attendees(count)`, capacity guard) stays correct without change, and an
already-built client can never mistake a waitlisted person for an attendee.

## 3. Series

`event_series` (new):

| Column | Meaning |
| --- | --- |
| `id`, `created_at`, `updated_at` | |
| `owner_id` | Recurring identity owner. Also `creator_id` on every generated occurrence, so the existing owner guard and RLS keep working for the owner. |
| `title`, `description`, `category_slug`, interest tags (series tag table mirroring `event_tags`) | Template copied onto new occurrences. |
| `place_id`, `location_name`, `address`, `lat`, `lng` | Usual venue (template). |
| `time_zone` | IANA name, required, validated like `notification_settings.time_zone` (`at time zone` must not raise). |
| `rule` | Structured schedule, **not** free-form RRULE in v1: `{ "freq": "weekly", "interval": 1–4, "weekdays": [1–7], "start_local": "HH:MM", "duration_minutes": 15–720 }`. |
| `starts_on`, `ends_on` | Local dates; `ends_on` nullable (open-ended). |
| `capacity`, `min_attendance`, `decision_lead_minutes`, `activity_details`, `card_style` | Session-rule template (§5). |
| `status` | `active` / `paused` (no new occurrences generated) / `ended`. |
| `rule_version` | Increments on every schedule change (§8). |

`event_series_hosts(series_id, user_id, role in ('owner','backup'), added_at)`. Exactly one owner row
(matches `owner_id`). Backup hosts may edit and cancel occurrences and manage the waitlist **only through
RPCs** that check `is_series_host(series, auth.uid())`. Direct `events` updates by a backup host are
still refused by the existing creator-only guard, which is what makes host revocation immediate.

`event_series_followers(series_id, user_id, created_at)`: follow = updates only (§9). Following never
creates an `event_attendees` or `event_participants` row; no trigger may do so.

**Generation.** Occurrences are materialized only inside a horizon (**recommend 4 weeks**, D-C) by
`generate_series_occurrences(p_series uuid default null, p_now timestamptz)`, a service-only function
run on series create/edit and by the existing daily cron. It is idempotent by
`unique (series_id, series_local_date)`, so concurrent runs cannot duplicate. It never recreates a
local date that exists in any status (a cancelled Thursday stays cancelled), and never generates past
`ends_on` or while the series is paused.

## 4. Occurrences

New nullable columns on `events`:

| Column | Meaning |
| --- | --- |
| `series_id` | null = one-off event. |
| `series_local_date` | The occurrence's local calendar date (identity within the series). |
| `time_zone` | IANA zone for **every** event. Backfilled to `America/New_York` (today's app-wide default) and required afterwards. Removes the hard-coded zone for event display. |
| `overridden` | `text[]` of template fields edited on this occurrence only (§8). |
| `cancel_reason` | `host` / `below_minimum` / `series_ended` / null. |

Venue override = editing `place_id`/location on one occurrence (recorded in `overridden`). Cancelled =
existing `status = 'cancelled'`, so refunds (`refund_on_cancel`), visibility for attendees
(`can_view_event`) and notifications keep working unchanged.

**Attendance** (series history, 4.5b): `event_attendees.attended boolean null`, set by a host RPC after
the occurrence ends (null = not recorded). It is never inferred from RSVP or directions, matching
founder open question 4's caution.

## 5. Session rules and the Readiness row

Per occurrence (copied from the series template for series occurrences):

| Field | Rule |
| --- | --- |
| `capacity` | Existing column. |
| `min_attendance` | Null, or 2 ≤ value ≤ capacity. |
| `decision_deadline` | Null, or ≤ `starts_at`. For series: `starts_at − decision_lead_minutes`. |
| `venue_status` | `confirmed` / `unconfirmed` (e.g. court not booked yet). |
| `decision` | `open` / `happening` (host confirmed, or the minimum was met at the deadline) / `not_happening`. |
| `card_style` | `readiness` (default) / `party_poster`. Owned by ticket 4.8; reserved here so series templates carry it. |

**Founder decision applied.** Event cards default to the **Readiness row**; hosts can toggle a **Party
poster**; there is **no calendar date block**. The Readiness row is computed by one function,
`event_readiness(event_id)`, so web, native and cards agree. Each number comes from its own field:

| Readiness value | Source |
| --- | --- |
| going | `count(event_attendees)` |
| spots open | `capacity − seats_taken` (§6.2; held offers and live paid holds are not "open") |
| more needed | `max(0, min_attendance − going)` |
| host confirms by | `decision_deadline` in the event's `time_zone` |
| waitlist | count of `waitlisted` (count only, no names) |

At the deadline (4.3 cron, service-only `decide_sessions(p_now)`): if `going < min_attendance` and the
host has not confirmed, the occurrence becomes `status = 'cancelled', cancel_reason = 'below_minimum',
decision = 'not_happening'`. The existing refund and visibility paths then apply, and attendees are
notified explicitly (§9), because the existing trigger is silent for service changes. A host confirm
before the deadline sets `decision = 'happening'` and blocks the auto-cancel.

## 6. Participant statuses

### 6.1 States

`event_participants(event_id, user_id, status, queue_position, offered_at, offer_expires_at, reason, updated_at)`,
primary key `(event_id, user_id)`.

| Status | Holds a seat? | Where it lives |
| --- | --- | --- |
| **going** | yes | `event_attendees` row (participant row deleted) |
| **interested** | no | `event_participants` |
| **waitlisted** | no | `event_participants`, `queue_position` from a global sequence (FIFO) |
| **offered** | **yes, until `offer_expires_at`** | `event_participants` |
| **declined** | no (`reason`: `declined` / `expired`) | `event_participants` |
| **left** | no | `event_participants` (can rejoin) |

Invariant, enforced by trigger: a user has a going row **or** a participant row for an event, never
both. Converting to going deletes the participant row in the same transaction.

### 6.2 Capacity accounting (one definition everywhere)

`seats_taken(event) = going + live offers + live pending paid holds`, where "live" means
`offer_expires_at > clock_timestamp()` / `tickets.expires_at > clock_timestamp()`. It is used by the join
trigger, `join_event`, `accept_offer`, `offer_next`, `reserve_ticket`, and the capacity-edit guard
(`capacity >= going + live offers`, extending `guard_owner_event_change`).

### 6.3 When and how long an offer holds capacity

- **From** the moment `offer_next` writes `status = 'offered'` (same transaction as the freed seat).
- **Until** the first of: acceptance (becomes going), decline, the person leaving, the occurrence being
  cancelled or ending, or `offer_expires_at`.
- `offer_expires_at = least(offered_at + offer_window, starts_at − offer_cutoff)`.
  **Recommend `offer_window = 2 hours`, `offer_cutoff = 30 minutes` (D-D).** No offers are made inside
  the cutoff; the freed seat just becomes open.
- An expired offer **stops holding at `offer_expires_at` exactly**, even before any sweep runs, because
  every check compares against `clock_timestamp()`. The sweep only tidies status and passes the seat on.

## 7. Atomic RPCs

All are `security definer`, `set search_path = public`, granted to `authenticated` (except where marked
service), and refuse suspended or closing accounts like `reserve_ticket` does. **Every seat-changing
path takes `select … from events where id = p_event for update` first.** That is the same lock the
existing join trigger, `reserve_ticket` and `set_event_price` use, so all of them (old and new)
serialize per occurrence.

| RPC | Behaviour (under the event lock) | Returns |
| --- | --- | --- |
| `join_event(p_event)` | Requires visible, published, not ended. Priced event → raise `payments:ticket_required` (§11). Already going → no-op. Own live offer → accept it. `seats_taken < capacity` (or no capacity) → insert going. Else upsert `waitlisted` with a new `queue_position` (keeping an existing position if already waitlisted). | `going` / `waitlisted` |
| `leave_event(p_event)` | Going → delete the attendee row, then `offer_next`. Offered → `left`, then `offer_next`. Waitlisted/interested → `left`. Not participating → no-op. | `left` |
| `set_interest(p_event, p_on)` | `interested` ↔ none. Never touches going, waitlist or seats. | status |
| `accept_offer(p_event)` | Locks the participant row too. Must be `offered` with `offer_expires_at > clock_timestamp()` and the event open. Then insert going and delete the participant row. Otherwise: `offer_expired` and the person stays off the list (no silent re-queue). | `going` / `offer_expired` |
| `decline_offer(p_event)` | Offered → `declined`, then `offer_next`. | `declined` |
| `offer_next(p_event)` *(internal, no grant)* | While `seats_taken < capacity`, before the cutoff, on a free published event: take the lowest `queue_position` waitlisted person who can still view the event and is not suspended/closing; set `offered` with an expiry (§6.3); notify (§9). | count offered |
| `expire_offers(p_now)` *(service; existing 15-min notifications cron)* | For each event with offers past expiry: lock the event, mark them `declined` (reason `expired`), notify, run `offer_next`. | count |
| `host_remove_participant(p_event, p_user)` | Series host or creator only. Removes going/waitlisted/offered; frees seat → `offer_next`. | |

**A stale offer can never displace a confirmed attendee.** Acceptance only converts a seat that the
offer itself already holds in `seats_taken`. Capacity can't be lowered below `going + live offers`. And
expiry and acceptance are decided under the same lock against the same clock.

## 8. Edit-this vs edit-this-and-future

- **Edit this occurrence** (one-off events behave exactly as today): update the `events` row. For a
  series occurrence, add the changed template fields to `overridden`. Backup hosts go through
  `update_occurrence(p_event, …)`.
- **Edit this and future** (`update_series_from(p_event, …)`): update the series template, effective
  from that occurrence's local date. Apply to each **future** occurrence on or after that date,
  skipping fields listed in its `overridden`. Past occurrences are never touched; the guard already
  forbids it.
- **Schedule changes** (weekday, time, interval) bump `rule_version`. Future occurrences with **no**
  going, offered, waitlisted, ticket or chat rows are deleted and regenerated under the new rule.
  Occurrences **with** participants are moved in place, which is a material change (§9), so their
  ids, attendees, tickets and chat survive. Recommended; part of D-E.
- **Cancel one occurrence**: `status = 'cancelled'` on that row only. The generator never recreates it,
  and the next occurrence is untouched.
- **End the series**: `status = 'ended'`, `ends_on` set; future occurrences after it are cancelled with
  `cancel_reason = 'series_ended'` (refunds and notifications follow existing paths).
- **Revoked host**: removing a `backup` row takes effect at once, since every host RPC re-checks
  `is_series_host`.

## 9. Notifications on material change (4.6)

Material change = start/end time, venue, cancellation (any reason), an offer, an offer expiring. These
are **not** material: description, title, capacity increases. All go through the existing `notify()`
(blocks, mutes, push types, dedupe), and push delivery keeps quiet hours and the daily cap
(`claim_push_batch`).

| Change | Recipients | Type (new types extend `check_notification_settings`) | Dedupe key |
| --- | --- | --- | --- |
| Time or venue changed | going + offered | existing `event_changed` | existing batch key `event_changed:<event>` |
| Cancelled by host | going + offered + waitlisted | existing `event_cancelled` | existing |
| Cancelled below minimum | going + offered + waitlisted | **new** `event_not_happening` | `event_not_happening:<event>` |
| Offer made | the offered person | **new** `event_offer` | `event_offer:<event>:<user>:<offered_at>` |
| Offer expired | that person | **new** `event_offer_expired` | `event_offer_expired:<event>:<user>:<offered_at>` |
| Series schedule change / occurrence cancelled | followers who are not already notified above | **new** `series_update` | `series_update:<series>:<rule_version or event>` |

Service-driven changes (cron, generator) call `notify()` explicitly with a null actor. They do not rely
on `notify_on_event_change`, which skips when `auth.uid()` is null. Followers are **not** notified for
each routine generated occurrence (D-F). Interested people get only cancellations (recommended; part
of D-F).

## 10. DST behaviour

- Series store **local wall-clock** time plus IANA zone. Each occurrence's `starts_at` is computed from
  `series_local_date + start_local` in `time_zone`, and `ends_at = starts_at + duration`.
- **Spring-forward gap** (e.g. 02:30 on 2026-03-08, New York): resolve to the same clock reading in the
  earlier offset, i.e. 03:30 EDT. Postgres `timestamp at time zone` and the app's `zonedTimeToUtc`
  agree on this (checked: both give 07:30Z).
- **Fall-back repeat** (01:30 on 2026-11-01): they **disagree**. The app resolves to the **first**
  instant, 05:30Z EDT (`src/lib/utils/timezone.ts:80–96`); Postgres `at time zone` returns the
  **second**, 06:30Z EST (checked on PostgreSQL 16). **The generator must not rely on bare
  `at time zone`.** It resolves explicitly to the first instant, to match the app (D-G), with a shared
  test vector so SQL and TS cannot drift.
- Occurrences are stored as instants, so a DST change between two occurrences keeps the local time
  (19:00 stays 19:00 local); the UTC instant shifts by an hour.
- Offer expiry, decision deadlines and reminders compare instants, so they are DST-safe. Display uses
  the event's `time_zone`.

## 11. Free sessions vs paid fulfillment

- **Waitlist, offers and `join_event` apply only to free events** (`price_cents is null`) in this design.
  Paid events keep today's flow unchanged: `reserve_ticket` (30-min hold, counted in `seats_taken`),
  Stripe, then `confirm_ticket` inserting the going row, and `mark_ticket_refunded` deleting it. If a paid
  event is full, the answer is "full", as today.
- The new join trigger lets `confirm_ticket`'s service insert through exactly as now: the ticket was
  counted as a live hold when reserved, and is now paid.
- `offer_next` is a no-op on priced events, so a refund or leave on a paid event never creates offers.
- `set_event_price` additionally refuses when anyone is `waitlisted` or `offered`; that extends the
  existing `payments:price_locked`.
- Series occurrences are free unless the host prices an individual occurrence with the existing
  `set_event_price` (series-level pricing is out of scope).
- Existing behaviour, flagged and unchanged: leaving a paid event frees the seat but does not refund,
  and the ticket stays `paid` (D-H).

## 13. Closing the legacy direct writes

**Phase 1 (ships with 4.4): every path enforces the same rules.**

1. Replace `check_event_join()`. Under the event lock it uses `seats_taken`. A direct insert by a user
   with a live offer converts it. Otherwise it is allowed only if a seat is open, else raises
   `This event is full`. Priced events still require a paid ticket. It also deletes any participant row
   for that user.
2. Add an AFTER DELETE trigger on `event_attendees` that runs `offer_next` (skipped while the event row
   itself is being deleted or is not published). Legacy deletes, refunds, account deletion cascades and
   moderation all hand the seat on.
3. Web: `repository.ts:1021/1025` switch to `join_event` / `leave_event` (demo twin at parity). Native:
   `api.ts:76/79` switch in 8.1b.

**What an old native build does in phase 1.** It joins while a seat is open. When the only "free" seats
are held by offers or paid holds, it gets the existing "This event is full" error, because it can't
join a waitlist. It can leave, and that triggers offers. It **cannot overbook or jump the queue.** Its
"going" display stays correct, because it reads `event_attendees` and that table still means going.

**Phase 2 (after the owner's go-ahead, D-I).** Drop the `insert` and `delete` policies on
`event_attendees` for `authenticated`, so the only writers are the definer RPCs, `confirm_ticket` and
`mark_ticket_refunded`. An old build then gets a permission error on join/leave. Because there is no
evidence a native build has shipped (§1), **recommend doing phase 2 in the same release as phase 1**,
unless the owner knows of installed builds. If builds exist, add a minimum-version check in the app
before phase 2.

## 14. RLS for attendee visibility

| Table | Who sees what |
| --- | --- |
| `event_attendees` (going) | Unchanged: anyone who can view the event (`can_view_event`), as today. |
| `event_participants` | Each person sees **their own** row. The creator and series hosts see all rows of their events. Everyone else sees counts only, via `event_readiness()`. No direct insert/update/delete for API roles; RPCs only. |
| `event_series` | Read like events: published series visible when their usual place is visible (same rule as `can_view_event`). Writes via RPCs; owner-only for owner fields. |
| `event_series_hosts` | Hosts of that series, and anyone who can view the series (names of hosts are public, as event hosts are today). Writes: owner only via RPC. |
| `event_series_followers` | Own rows only; hosts see a count. |

Moderators keep existing powers through `moderate_target` on occurrences; series-level moderation
(hide a whole series) is listed as D-J.

## 15. Test plan

Database tests run on PGlite (`tests/helpers/pglite.ts`) for logic and RLS. **Race tests run on real
PostgreSQL through `tests/helpers/postgres.ts`** (built by ticket 0.1a: `testDatabaseUrl()`,
`createTestDatabase(url)` returning two independent connections `a`/`b` plus `connect()`). Each
connection acts as an API user via `set role authenticated` and `request.jwt.claim.sub`, the way the
PGlite `queryAs` helper does. Tests skip loudly without `TEST_DATABASE_URL` and fail in CI, and a
skipped run never counts as passing.

**Concurrency (two connections, real Postgres), in the batch that introduces each path:**

1. Last seat: two `join_event` calls → exactly one going, the other waitlisted.
2. Direct PostgREST-style insert into `event_attendees` racing an `accept_offer` for the last held
   seat → the offer holder is going; the direct insert gets "full".
3. `expire_offers` racing `accept_offer` exactly at `offer_expires_at` (frozen and real clock) →
   exactly one outcome: going, or expired-and-passed-on. Never both, never neither.
4. Double accept of the same offer from two connections → one going row, one no-op.
5. Leave racing a new join for the freed seat → the seat goes to the next waitlisted person (offer),
   not the newcomer.
6. Host lowers capacity racing a join → never `going + live offers > capacity`.
7. Paid event: `reserve_ticket` racing another `reserve_ticket` for the last seat (existing behaviour
   kept) and `confirm_ticket` still inserting the going row under the new trigger.
8. Two concurrent `generate_series_occurrences` runs → no duplicate local dates.
9. Cancel an occurrence racing joins and offers → no going rows added after cancellation; offers stop.
10. Duplicate notification delivery: `offer_next` / `expire_offers` run twice → one notification per
    offer (dedupe key).
11. 1,000 alternating join/leave calls across two connections on a capacity-5 event → invariants hold
    at the end (`going ≤ capacity`; no user both going and participating; queue order preserved).

**Logic and RLS (PGlite):** every state transition in §6–7; offer cutoff near start; DST vectors
(§10, spring gap, fall-back first-instant, occurrences across the change); frozen-clock decision
deadline (just before, at, after; host confirm); edit-this vs edit-future with overridden fields;
cancel one leaves the next intact; revoked backup host denied at once; follow never creates
attendee/participant rows. RLS as anon, owner, backup host, another user and moderator: participants
see only their own row, hosts see all, counts via `event_readiness()`. Price lock with
waitlisted/offered. Account deletion cascades participants and series rows (update the deletion count
tests). Demo repository twins at parity for every RPC.

**Real code paths:** web actions `src/server/actions/events.ts` join/leave through the repository to the
RPCs (no direct table writes left, asserted by a source check); native `api.ts` in 8.1b.

### A1.2 Capacity is enforced on every admission path

**Definition.** `seats_taken_at(event, at) = count(event_attendees) + count(tickets where status =
'pending' and expires_at > at)`. A hold is live strictly before its `expires_at`; at that instant it
is dead. The committed `findmaxxing_private.seats_taken(event)` (0051) stays as the read-model entry
point and becomes `seats_taken_at(event, clock_timestamp())`. Both stay revoked from every API role.

**The invariant.** For an event with a capacity, `seats_taken_at(event, now) <= capacity` after every
committed transaction. Every writer that could break it holds the event row lock while it decides
(A1.9).

**What a paid ticket is.** A `paid` ticket is *eligibility to be admitted* (it satisfies
`payments:ticket_required`). It is **not** a held seat. Today a buyer who leaves keeps a `paid` ticket
(leaving does not refund), and their seat can be taken by someone else. Coming back with that old
ticket is an ordinary admission and is refused when the event is full. Only a live `pending` hold
reserves a seat.

**Correction to revision 1.** Revision 1 said `confirm_ticket` can seat buyers above capacity after a
host lowers capacity. That was wrong. `check_event_join()` already refuses any insert once the going
count reaches capacity, and `confirm_ticket` turns that refusal into `refund_pending`. The real gap is
the other one: a host can lower capacity while a paid hold is live, and the buyer then pays and is
refunded instead of seated. Nothing is over-seated today.

**Rules for the capacity migration** (proposed number 0053; one migration, no series tables):

1. **`check_event_join()` (every `event_attendees` insert).** Keep every existing rule, its order and
   its error strings. Replace the attendee-only count: after taking the event lock, read
   `v_at := clock_timestamp()` once and refuse with `This event is full` when
   `capacity is not null and seats_taken_at(event, v_at) >= capacity`.
   - **No exemption by ticket.** A `paid` ticket passes the ticket rule and then meets the same
     capacity check as anyone else.
   - **The host's ticket exemption stays** (the creator needs no ticket). **Capacity applies to the
     host too**, as it does today: a host who left their own full event cannot push back in.
   - The function is already `security definer`, so it can call the private helper. No grant changes.
2. **`confirm_ticket()` (fulfilment).** Reordered to buyer, then event, then ticket (A1.9), with the
   same four results (`unknown`, `duplicate`, `refund`, `confirmed`) and the same refund-pending
   contract:
   1. Read the ticket's `id`, `event_id` and `user_id` for the session **without locking**. None:
      `unknown`.
   2. If the ticket has a buyer, take `account_close:<buyer>`. The attendee insert's trigger
      (`block_suspended_writes`, 0027) takes this lock for the row's user even for a service
      caller, and `prepare_account_deletion` holds it while it expires that buyer's pending
      tickets, so it has to come first.
   3. If the event still exists, `select … from events where id = v_event for update`.
   4. `select … from tickets where id = v_ticket for update` and **re-read** it. It must still carry
      this session, this event and this buyer. A different session: `unknown`. A buyer that is now
      null (anonymized) or an event that is gone: continue on the refund path below.
   5. Read `v_at := clock_timestamp()` now, after all three locks. Status other than
      `pending`/`expired`: `duplicate`. `expired`, or `expires_at <= v_at`, or amount mismatch, or no
      event, or no buyer: `refund_pending`, return `refund`.
   6. Otherwise set the ticket `paid`, then insert the attendee row. Its capacity trigger (rule 1)
      now counts the *other* people going and the *other* live holds, because this buyer's own hold
      has just stopped being `pending`. In the normal case that is below capacity and the buyer is
      seated: `confirmed`.
   7. If the insert is refused for any reason (the event was cancelled or ended, it is full, or the
      buyer's account is closing: `account_deletion_in_progress`), the existing handler applies
      unchanged: `refund_pending`, return `refund`. A late, cancelled, closing-account or otherwise
      unfulfillable confirmation of a payment that succeeded is always refunded, never seated.
3. **`reserve_ticket()`.** Same behaviour and errors, with three changes in how it gets there:
   - it takes `account_close:<caller>` **first**, before the event lock. Today its ticket writes
     reach the same trigger after the event and a ticket row are already locked;
   - after the event lock it reads `v_at` once, sweeps holds with `expires_at <= v_at`, and counts
     with `seats_taken_at(p_event, v_at)` instead of its own inline count;
   - a new hold expires at `v_at + 30 minutes`, not `now() + 30 minutes`, so a caller who waited
     for the lock still gets the full hold.
4. **Capacity floor on edit.** A host cannot lower capacity below `seats_taken`, so a live hold cannot
   be stranded. `guard_owner_event_change()` is a `security invoker` function and the helper is revoked
   from API roles on purpose, so the guard **must not call it**. Instead:
   - a separate trigger function `findmaxxing_private.guard_event_capacity_floor()`, `security
     definer`, `set search_path = public`, owned by the migration role, fired `before update of
     capacity on public.events`;
   - it runs under the row lock the `UPDATE` already holds, reads `v_at` once, and raises the existing
     string `Capacity cannot be below the existing attendee count` when
     `new.capacity < seats_taken_at(old.id, v_at)` (the same string keeps the web, native and demo
     error mapping; the UI copy may say "people going or paying now");
   - the attendee-count check inside `guard_owner_event_change()` is removed in the same migration so
     there is one floor, not two;
   - it applies to every caller, including the service role. A series template edit (4.5a) that would
     put an occurrence below its seats taken leaves that occurrence's capacity as it is and reports it
     to the host; it does not fail the whole edit.
5. **Demo twin.** The demo repository applies the same four rules with the same error keys, and never
   returns or stores `waitlisted`.

### A1.4 Series and occurrences (4.5a, 4.5b)

§3, §4, §8 and §10 apply with these reductions and additions.

- `event_series`, `event_series_hosts`, `event_series_followers` as specified. Backup hosts act only
  through RPCs; "manage the waitlist" is removed from their powers.
- Generation, idempotency (`unique (series_id, series_local_date)`, a plain unique index so it can
  stay the `on conflict` arbiter), the 4-week horizon, never recreating a local date that exists in
  any status, and the explicit first-instant DST rule are unchanged.
- Following never creates an attendee row; no trigger may do so. Follow and going are separate states
  in every read model and UI (founder decision).
- `event_attendees.attended` (host-recorded, never inferred) stays in 4.5a for series history only.
  **It does not satisfy R4.** R4 (weekly memories) requires the person's own explicit report, under
  its own contract. A host's mark alone never creates a memory and is never shown as the person's own
  statement.

**What the generator writes.** A generated occurrence is created the way a one-off event is today
(`create_event_with_details`, 0036): the series owner is inserted as going, and `sync_event_chat`
(0020) therefore creates the occurrence's conversation with the owner as its only member. So every
occurrence has one attendee row and one empty conversation from the start, and "has no going or chat
rows" can never be the test for whether it may be deleted.

**Committed and uncommitted.** Checked under the occurrence's event lock. An occurrence is
**committed** if any of these is true; otherwise it is **uncommitted**:

| # | Committed when | Why |
| --- | --- | --- |
| a | anyone other than the series owner has an attendee row | someone chose to come (a backup host who joined counts) |
| b | any `tickets` row references it, in any status | payment history keeps a stable id |
| c | its conversation has at least one `messages` row | that is chat history; an empty conversation is not |
| d | an outing is anchored to it (5.5) | see 5.0 Amendment A1 |
| e | `status` is not `published`, or it has started | cancelled rows are the record that stops the date being recreated; the past is never touched |
| f | `overridden` is not empty, `decision` is not `open`, or `attended` is recorded on any row | a host acted on this occurrence |
| g | any other row references it by foreign key, apart from rows the generator itself wrote (its tags, the owner's attendee row, the empty conversation and the owner's membership of it) | nothing a person made is silently deleted |

Rule g is enforced by a test that lists every foreign key that references `events` from the catalog
and fails when one is not classified, so a table added later cannot be missed.

**Schedule change** (`update_series_from`, weekday, time or interval; bumps `rule_version`). It has
two phases. Nothing is written until the whole plan exists and has been checked.

*Locks, in A1.9's order:* the account locks (the series owner and the acting host), the series row,
every future occurrence of the series in ascending `id`, then each of those occurrences'
conversation rows `for update`, in the same order.

*Classification.* Each occurrence is classified under those locks. For rule c the messages are
re-read **after** the conversation lock. A message insert holds a key-share lock on its
conversation, which conflicts with ours, so there are only two orderings:

- the send commits first: we see the message, the occurrence is committed and is preserved with it;
- we hold the lock first: the send waits, and after an uncommitted occurrence and its conversation
  are deleted it fails on its foreign key. The repository and the client must report that failure;
  the message is never shown as sent.

If the conversation lock cannot be taken in this order for any reason, the occurrence is treated as
committed and kept.

*Phase 1: plan.* Read-only.

1. **Retained dates** are the local dates of rows that will not move: cancelled occurrences, started
   ones, and occurrences with `schedule` in `overridden` (a host's one-off change, or one kept by an
   earlier schedule change). Nothing may be moved onto a retained date.
2. **Movable** occurrences are the committed, published, future ones that are not retained.
   **Uncommitted** future occurrences will be deleted, so their dates are free.
3. **Candidate dates** are the new rule's local dates from the effective date to the horizon, minus
   the retained dates, keeping only those whose start under the new rule is in the future.
4. **Assignment**, deterministic:
   - first, every movable occurrence whose own date is a candidate keeps that date (it changes time
     only);
   - then the rest, in ascending old date, each take the unclaimed candidate **nearest** their old
     date (a tie goes to the later one), within 6 days.
5. **No destination.** A movable occurrence with no candidate is **kept exactly as it is**: same id,
   date and time. Its date becomes a retained date. If another occurrence had been assigned that
   date, the assignment is recomputed from step 3 with the larger retained set. The retained set
   only grows, so this ends after at most one round per movable occurrence.
6. **Check.** The final dates of every row of the series that will exist afterwards (retained, kept,
   moved) must be pairwise distinct. If they are not, the function raises and nothing is changed.

*Phase 2: apply*, in one transaction, only after the check:

1. Uncommitted future occurrences are deleted, with their empty conversations.
2. Moves are applied in two steps so the unique index never sees a duplicate: the moving rows'
   `series_local_date` is set to null (nulls never collide), then each gets its final date,
   `starts_at` and `ends_at`. Ids, attendees, tickets, chat and outing anchors are untouched.
3. Kept occurrences get `schedule` added to `overridden`, and the result lists them as "kept at its
   old time" for the host, who can edit or cancel each one. Keeping is not a material change, so
   nobody is notified about it.
4. Regeneration creates the new rule's dates that have no row, with `on conflict do nothing`. A date
   held by any row, cancelled included, is skipped, so a cancelled date is never recreated.
5. The function ends by asserting that no row of the series has a null local date.

A moved occurrence is a material change (A1.5). A deleted uncommitted one is not: only the owner was
on it.

Occurrence ids are stable for anything a person has touched, which 5.5 and 6.3 rely on.

### A1.5 Notifications (4.6): one path per change

**Recipients and types.**

| Change | Recipients | Type |
| --- | --- | --- |
| Time or venue changed | going | existing `event_changed` |
| Cancelled by host | going | existing `event_cancelled` |
| Cancelled below minimum | going | existing `event_not_happening` (shipped in 4.3) |
| Series schedule change, or an occurrence cancelled | followers who are **not** going to an affected occurrence | **new** `series_update` |

A follower who is going to an affected occurrence gets the event notification for it and **no**
`series_update` for the same change. Followers are not notified per routine generated occurrence (D-F).

**Who sends.** Exactly one sender per change, chosen by the kind of session:

- **Authenticated session** (`auth.uid()` is set: a host editing directly, or through a series RPC,
  which is `security definer` but keeps the caller's `auth.uid()`). The row trigger
  `notify_on_event_change` is the only sender for going recipients. Series RPCs **do not** call
  `notify()` for them.
- **Service session** (`auth.uid()` is null: cron, the generator, `decide_sessions`). The trigger is
  silent, as today (0021), and the function calls `notify()` explicitly.
- `series_update` is sent once per change by the function that made the change, in either session.

**Why a change cannot be delivered twice, and two changes are not merged.** `events` gains
`change_seq integer not null default 0`, incremented by a `before update` trigger whenever a material
field changes (start, end, any venue field, or status leaving `published`). Every send uses a
**dedupe key that names the change**:

| Type | Dedupe key |
| --- | --- |
| `event_changed` | `event_changed:<event>:<change_seq>` |
| `event_cancelled`, `event_not_happening` | existing keys (an event is cancelled once) |
| `series_update` (schedule) | `series_update:<series>:v<rule_version>` |
| `series_update` (occurrence cancelled) | `series_update:<series>:cancel:<event>` |

`notify()` inserts with `on conflict (user_id, dedupe_key) do nothing`. So a retry, a rerun cron, or
both paths firing by mistake produce one notification per recipient per change. A second legitimate
edit has a new `change_seq`, so it is a new notification and can be pushed again, within the existing
quiet hours and daily cap. This replaces today's `batch_key` on `event_changed`, which folds a second
edit into the first unread row and never pushes it; that change to an existing type is called out in
A1.8 for the reviewer.

**Checks before any content is generated for a recipient.** A null actor skips the block check inside
`notify()`, so the sender does these itself, per recipient, under the event lock:

1. the recipient is still going (or still following, for `series_update`);
2. the recipient can read the event or series **now**, evaluated for that recipient (a
   `findmaxxing_private` variant of `can_view_event` that takes the user, since the public one reads
   `auth.uid()`). Revoked visibility means no notification and no label;
3. neither the recipient nor the host responsible for the change (the series owner, or the event's
   creator) has blocked the other.

The label is the event or series title only. No attendee names, venue notes or reasons.

### A1.9 Lock order and the expiry boundary

**One order, for every path:**

1. `account_close:<user>` advisory locks, in ascending user id when a path needs more than one: the
   acting user, and any user for whom the path will insert an attendee row (the buyer in
   fulfilment; the series owner in generation);
2. the series row (4.5a);
3. event rows, in ascending `id` when a path needs more than one;
4. ticket rows;
5. attendee rows;
6. outing rows in ascending `id`, then their child rows (5.0 Amendment A1);
7. conversation rows, in the order of their events, then message and notification rows.

A path never takes a lock from an earlier line while holding one from a later line.

**Where the account lock comes from.** `block_suspended_writes()` (0027) is a `before` row trigger
on `tickets`, `events`, `event_attendees`, `messages` and others. For a signed-in caller it takes
`account_close:<auth.uid()>`. On an `event_attendees` insert it also takes `account_close:<the row's
user>`, whoever the caller is, service role included. `prepare_account_deletion()` takes the same
lock for the closing user first, then cancels their events and expires pending tickets. So any path
that reaches one of those triggers after it already holds an event or ticket lock is in the reverse
order to account closure. New and replaced functions therefore take the account lock themselves, at
the start.

**One clock.** Every decision about whether a hold is live is made under the event lock with a single
`clock_timestamp()` read **after** the lock is acquired, and the same value is used for fulfilment and
for seat accounting in that section. `now()` is the transaction's start and can be long before the
moment the lock was granted, so it is not used for these decisions. Because the sections are
serialized by the event lock and the clock does not go backwards between them, two sections can never
both treat the same seat as theirs.

**Audit of the paths at head 0051.**

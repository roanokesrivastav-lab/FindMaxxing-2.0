## Events 4.0 A1 revision 2

**Approved with required changes.** The shared capacity check, retention of legacy client writes, new private capacity-floor trigger, and per-change notification model address the earlier review. The capacity and series sections need the following targeted amendments before the affected migrations start.

1. **Include the buyer's advisory lock in the actual lock order.** The attendee insert trigger takes `account_close:<buyer>` even for service confirmation. `prepare_account_deletion` takes that lock first and expires the buyer's pending tickets. With the proposed `confirm_ticket` order, confirmation can own the ticket and wait for the buyer lock while account closure owns the buyer lock and waits for the ticket. `reserve_ticket` also reaches an actor-locking trigger on its ticket writes. Define confirmation's order as buyer advisory lock → event → ticket → attendee. Discover the buyer from the preliminary ticket read and revalidate identity, session, and event after locking. An anonymized or closing buyer follows the existing refund disposition when payment has succeeded. Pre-acquire the actor lock on reservation before locking events or tickets. In series create/generation paths, account for the locks taken by host attendee insertion under both service and authenticated callers, and take required account locks before series/event locks. Add a controlled confirmation-versus-buyer-closure race and verify the reservation order. Preserve the current account-deletion safeguards. [Account-deletion trigger](../../supabase/migrations/0027_account_deletion_lifecycle.sql)
2. **Plan series moves before any mutation and serialize chat classification.** The nearest-date assignment can give an earlier occurrence a later occurrence's old date. If the later occurrence then has no valid destination, the keep rule would leave both on the same date. Reserve retained dates and produce a complete conflict-free assignment before applying moves, or conservatively keep the conflicting occurrences and explain that result. Test two committed occurrences competing for a date when one must stay. When classifying an empty conversation as deletable, serialize against new messages. A message references the conversation, so the event row lock alone does not protect the empty-chat check. Lock the conversation before re-reading messages and deleting, or preserve the occurrence when safe serialization cannot be established. A send that commits first must preserve its message. A send that loses the race must fail without claiming success. Add both orderings to the real PostgreSQL proof. [Series amendment](4.0.md)
3. **Make the test proof specific to the guard under review.** A blanket assertion that all cases 1–9 fail against the old functions cannot hold. The old direct-join and reservation paths already serialize last-seat claims. Keep regression tests for those cases, then remove the relevant lock, capacity floor, or re-read for each targeted mutation proof. Use the post-lock time when setting a new reservation's expiry as well as when evaluating existing holds, so a long-running transaction still creates the intended hold window. [Events proof and lock audit](4.0.md)

**Decisions on the four open points.** Keep the six-day rule and retain an occurrence when it has no safe destination. Send one notification per legitimate material change and dedupe retries of that change. Treat a conversation with a message as chat history and preserve it under the race rule above. Keep the existing capacity error string for client compatibility.

**Handoff contract.** Keep 0053 focused on paid and free admission invariants, event and buyer lock order, and the demo equivalent. Keep series generation and schedule reconciliation in the proposed 0054 and notifications in 0055. Preserve existing client permissions, refund outcomes, and reserved 0052. ## Outings 5.0 A1 revision 2

**Approved with required changes.** Use `ON DELETE SET NULL` with an atomic `removed` flag and preserve the account-deletion cascade. Standing constraints inform the group and a member's explicit item veto is what blocks locking. Votes from removed or departed members stop counting for future decisions. The explicit veto still applies to both manual and deadline locks.

1. **Apply event access rules to derived anchor data.** A joined member can currently read the proposed outing row, which contains the anchor ID and the automatically copied event window. Event RLS on a later detail query cannot redact values already stored on an outing or a saved itinerary. Define an API projection that keeps raw anchor references and event-derived date/time behind current event authorization, including direct PostgREST reads and reads of previously saved itineraries. A member without event access can see the generic anchor flag and separately authored shared planning data. Add tests where a joined member never had access to the event and where access is revoked after an itinerary is saved. [Outings privacy and lifecycle](5.0.md)
2. **Account for implicit foreign-key locks.** The proposed 6.3 path takes the outing lock and reads the event without locking it. An itinerary write with an event foreign key would still acquire an event key-share lock. Event deletion can hold the event lock while waiting for the outing, so the two writes can deadlock. Use the outing as the canonical event reference and avoid an event foreign key on itinerary versions, or explicitly take the event lock before the outing on every path that needs it and recheck the anchor after locking. Document the selected shape jointly in 5.5 and 6.3. Also avoid acquiring the parent outing lock in a row-level update/delete trigger after the child tuple is locked. Use RPCs and explicit privileged maintenance paths that lock the outing first, with a fail-closed guard if needed. Cover direct service writes and account-deletion cascades in the lock audit. [Outings lock order](5.0.md) · [Itinerary persistence](6.0.md)

**Handoff contract.** Keep the Must Events dependency gate and the existing outing roles, invites, shortlist, and veto behavior. Scope anchor storage and privacy to 5.5 and carry the contract into 6.3. Cover deletion versus itinerary save, unauthorized anchor data through actual API projections, and the existing membership, vote, and anchor races. A concise patch to the two briefs and a targeted preflight are sufficient.

## 2. Model

```
outings ──< outing_members ──< outing_votes >── outing_items
   │    ──< outing_invites                (hashed tokens)
   │    ──< outing_constraints            (member-declared hard limits)
   │    ──< outing_changes                (append-only log)
   │    ──  outing chat                   (conversation kind 'outing')
   └── anchor_event_id → events (4.0 occurrence, optional)
```

`outings`:
- `id`, `owner_id`, `title` (1–80), `note` (≤ 280, public to members);
- `time_zone` (IANA, required); `starts_local` / `ends_local` (optional plan window);
- `decision_deadline` (instant, optional);
- `status`: `draft` → `deciding` → `locked`; `cancelled` from any state;
- `locked_item_id`, `locked_at`, `locked_by`;
- `anchor_event_id` (nullable; set only by 5.5), `anchor_flag` (`null` / `moved` / `cancelled`);
- `created_at`, `updated_at`.

`outing_members(outing_id, user_id, role in ('host','member'), state in ('joined','removed','left'),
joined_at, removed_at, removed_by)`. The owner is a `host`; hosts can add hosts. Primary key on
`(outing_id, user_id)`. A `removed` row is kept so a removed person can't rejoin through an old invite.

## 3. Invites

- `outing_invites(id, outing_id, token_hash, created_by, created_at, expires_at, revoked_at, max_uses, uses)`.
- The token is 32 random bytes (base64url) shown once in the link. Only its SHA-256 is stored.
- **Shareable link (decision O-1):** multi-use. It expires after **7 days** by default (host can choose
  1–14 days) and is revocable. Total uses are capped at the member cap.
- **Member cap (decision O-2): 12 joined members** per outing.
- `claim_invite(token)`: authenticated only, via a definer RPC. It checks that the token exists, isn't
  revoked or expired, isn't over cap, the outing isn't cancelled or locked (O-3: no joining after lock),
  the claimer isn't `removed` from this outing, isn't blocked either way with any host, and isn't suspended
  or closing. Then it inserts a `joined` member and increments `uses`, under a lock on the outing row.
  Failures return one generic "This invite isn't valid any more", so a token can't be probed for its reason.

**Signed-out friends (5.4):** `/o/<token>` shows only the outing title, the inviter's display name and
"Sign in to join". No shortlist, members or votes are shown until claimed. **Identity is required before
voting.** After sign-up or sign-in the token is carried through the auth redirect, using the existing
`safeAuthNext`, and claimed once. The token is never logged; links get `Referrer-Policy: no-referrer`.

## 4. Shortlist items

`outing_items(id, outing_id, place_id, added_by, reason (≤ 140, written fresh), created_at, removed_at)`:
- unique `(outing_id, place_id)` among live items;
- **5 to 12 items** per outing (decision O-4: at least 2 to open voting, at most 12).

**What an item may reference (decision O-5): only places every current member can view: published,
`visibility = 'public'`.** Locals-only, followers-only, trusted, private and draft places (3.3) can't be
added. That is the simplest way to guarantee a member never learns of a place through the outing that
they couldn't see otherwise. Each item is re-checked at read time; a place that becomes hidden or removed
shows "No longer available" and can't win.

## 5. Adding from saves (3.1 not built yet)

- **5.2 copies only the place id.** "Add from my saves" lists the viewer's own saves and lists,
  owner-only as today. Adding creates an item with `place_id`, `added_by` and the `reason` the member
  types in the add dialog.
- **Never copied, now or after 3.1:** the source list name, the save's private note, personal tags,
  `recommended_by`, the source URL, the save status, or anything else 3.1 adds as "Only you". The
  database enforces this structurally: `outing_items` has no column that could hold those fields, and the
  add RPC takes only `(outing_id, place_id, reason)`.
- **Before 3.1 lands,** 5.2 works with today's saves and lists. After 3.1, the add dialog may *show*
  the user their own private note as a reminder (client-side, never sent). Required test: a private note
  and list name never appear in any outing response, notification, invite page or chat (§11).
- Members can also add from search (any public place), not only from saves.

## 6. Votes, constraints, deadline and lock (5.3)

- `outing_votes(outing_id, item_id, user_id, choice in ('yes','fine','cant'), constraint_kind null, updated_at)`.
  One **current** vote per member per item: primary key `(item_id, user_id)`, upserted. History goes to
  `outing_changes`.
- **Hard constraints veto instead of being outvoted.** A `cant` vote may carry a `constraint_kind`
  (`dietary`, `accessibility`, `budget`, `other`). A `cant` with a constraint **vetoes** the item: it can't
  win, whatever the counts. A plain `cant` counts against the item. Members can also declare standing
  constraints in `outing_constraints(outing_id, user_id, kind, note ≤ 140)`, visible to members, so
  others know before suggesting.
- **Visibility of votes (decision O-6):** members see each item's counts **and who voted what**. Open
  ballots fit friends planning together and make the veto accountable. These are the members' own
  votes, not a summary of friends' opinions about a place: no review text and no "friends liked this".
  Non-members see nothing. There are **no match scores** of any kind (founder decision).
- **Ranking:** vetoed items are excluded. The rest sort by `yes`, then `yes + fine`, then fewest `cant`,
  then earliest added. The tie-break is deterministic and shown ("tied; the host decides" when the top
  two are equal on the first three keys).
- **Lock:** a host locks manually, or at `decision_deadline` the service-only `lock_due_outings(p_now)`
  locks the top-ranked item. If the top two are tied, it notifies hosts to choose instead of guessing.
  Locking sets `status = 'locked'`, `locked_item_id`, `locked_at` and `locked_by`, under `select … for
  update` on the outing row. **Votes, item changes and claims all take the same lock and refuse when
  `locked`, so simultaneous edits can't replace a locked decision.**
- **Unlock (decision O-7):** a host can reopen it once, with a reason that is logged; the reason is shown
  to members.
- `outing_changes(id, outing_id, actor_id, kind, payload jsonb, at)`: append-only (a trigger blocks
  update/delete). It records add/remove item, vote, constraint, lock, unlock, member removed/left,
  invite revoked, anchor flag. Members can read it.

## 7. Anchor to an event occurrence (5.5)

- `start_outing_from_event(p_event)`: the caller must be **going** to that occurrence (`event_attendees`,
  4.0 D-B). It creates an outing with `anchor_event_id = p_event`, `time_zone` = the occurrence's
  `time_zone` (4.0 §4), and the window starting at the occurrence's end (default). The fixed start time
  becomes a locked constraint for planning (6.0 §4).
- Occurrence ids are stable (4.0 D-A). Occurrences with participants are never regenerated (4.0 §8).
- **Material change (4.0 §9):** when the anchored occurrence's time or venue changes, set
  `anchor_flag = 'moved'`; when it's cancelled, set `'cancelled'`. Both happen in the same transaction as
  the event update (a trigger on `events`), and members are notified (`outing_anchor_changed`). The
  outing isn't deleted. Itineraries anchored to it are invalidated (6.0 §5).
- The outing never RSVPs anyone to the event. Membership and attendance are independent.

## 8. RLS and direct-API attack cases

Every table: RLS on, **no direct writes for API roles**; writes only through definer RPCs that call
`is_outing_member(outing, auth.uid())` (`joined` state) and, where needed, `is_outing_host`.

| Table | Read |
| --- | --- |
| `outings` | Joined members, plus title-only through the invite landing RPC (§3). |
| `outing_members` | Joined members see joined members and roles. A removed person sees nothing. |
| `outing_items`, `outing_votes`, `outing_constraints`, `outing_changes` | Joined members only. |
| `outing_invites` | Hosts only, and never `token_hash` (column privileges). |

Attack cases the tests must cover (direct PostgREST calls as a real user):
- a non-member reads any outing table;
- a removed member reads after removal (page, API, chat, notifications);
- a member votes on another outing's item;
- forging `user_id` on a vote;
- adding a private, locals or draft place;
- adding when locked;
- claiming an expired, revoked or over-cap invite, or as a removed member;
- guessing tokens (generic failure, rate-limited claims);
- reading `token_hash`;
- a blocked user claiming the invite of someone who blocked them;
- reading another user's saves through an outing.

## 9. Chat and notifications

- **Outing chat (decision O-8):** reuse messaging with a new conversation kind `'outing'` and an
  `outing_id`. This relaxes 0020's group/event check in a new migration. Membership syncs from
  `outing_members` the way 0020 syncs event attendees. This is "friends discuss plans among themselves".
- **Notifications** (new types added to `check_notification_settings`):
  - `outing_invited` (when a member adds a known user);
  - `outing_deadline_soon` (2 hours before);
  - `outing_locked`;
  - `outing_tie` (hosts);
  - `outing_anchor_changed`;
  - `outing_removed` (to the removed person, with no content).
  All go through `notify()` (blocks, mutes, quiet hours, daily push cap) with dedupe keys per outing and
  event. Labels carry the outing title and never a place's private context.
- **Realtime:** polling for v1 (decision O-9: every 15 s while the outing page is visible, paused when
  hidden). Supabase Realtime later if needed.

### A1.2 One lock order across events and outings

The order is the one in [4.0 A1.9](4.0.md#a19-lock-order-and-the-expiry-boundary): advisory account
lock, series, **event rows (ascending id), ticket rows, attendee rows, outing rows (ascending id),
outing child rows** (members, items, votes, constraints, itinerary versions), then conversations and
notifications. Any path that needs both an event and an outing takes the **event first**.

| Path | Locks, in order | Notes |
| --- | --- | --- |
| `start_outing_from_event` (5.5) | caller's account lock → event `for update` → the caller's own attendee row `for update` → insert outing, its anchor row, owner membership, change log | all checks are repeated under the locks (A1.3). The anchor row's foreign key takes a key-share lock on the event, which this path already holds |
| Direct leave (attendee delete, legacy path) | the attendee row | waits for, or is seen by, anchor creation because both lock that row |
| Series regeneration (4.5a) | series → each candidate occurrence in ascending id | checks for an anchor **after** taking the event lock, before any delete |
| Material change on an event (trigger, 5.5) | event (the `UPDATE` itself) → each anchoring outing in ascending id `for update` → its anchor row → that outing's itinerary versions | event → outing, never the reverse |
| Event delete (owner, cascade, moderation) | event (the `DELETE`) → anchoring outings in ascending id → their anchor rows (flag, then the foreign key's `set null`) | A1.4 |
| Vote, item, claim, constraint, manual lock, unlock, `lock_due_outings` (5.1–5.3) | the outing row → its child rows | **never take an event lock** |
| Account closure of a member (`prepare_account_deletion`) | the user's account lock → each outing they belong to in ascending id → their rows in it | runs before the profile cascade, so the cascade finds nothing left to delete in outing tables (A1.5) |
| Direct write by the service role to an outing child table | none | **refused** by the guard in A1.5 unless it goes through an RPC that locked the outing first |
| Itinerary generation and edits (6.x) | the outing row → itinerary versions | read the anchored event with a plain `select`, no lock. **Itinerary versions have no foreign key to `events`**, so a save takes no event lock of any kind (below) |

**The outing is the only reference to the event.** The anchor lives in one place:
`outing_anchors(outing_id primary key → outings, event_id → events on delete set null, flag,
anchored_by, anchored_at)`. Nothing else in the outing or itinerary tables has an event column.
6.0 §5's `anchor_event_id` on `outing_itineraries` is withdrawn (noted in [6.0](6.0.md)); an
itinerary's fixed stop says "the outing's anchor" and nothing more.

This matters for locks as well as privacy. A foreign key to `events` on an itinerary version would
make every save take a key-share lock on the event while holding the outing lock. An event delete
holds the event and waits for the outing, so the two would deadlock. With no such key, an itinerary
save takes outing → itinerary rows and nothing on the event side.

**Why outing paths may read the event without locking it.** An outing path that needs the anchored
event's time reads it unlocked and may read a value that is about to change. That is safe because the
event's material-change trigger then needs the outing row lock: it waits for the outing path to
commit, and only then flags the outing and invalidates its itineraries. To make that true the trigger
must (1) lock the outing row first, and (2) run the invalidation as a **later statement**, so that it
sees an itinerary version the outing path committed while the trigger was waiting. Every itinerary
write must hold the outing lock. With that, no path locks an outing and then waits for an event.

### A1.3 Creating an anchor (5.5)

`start_outing_from_event(p_event)`, in this order, all in one transaction:

1. Lock the event row. Not found: generic refusal.
2. Under that lock, check again: `status = 'published'`, it has not ended, and `can_view_event` holds
   for the caller. A cancelled, removed, past or no-longer-visible occurrence is refused with one
   generic error that does not reveal which it was.
3. Lock the caller's **own** attendee row for that event. No row: refused (`You need to be going`). A
   direct leave that is deleting that row either committed first (no row, refused) or waits until
   this transaction ends.
4. Create the outing, its `outing_anchors` row, the owner's membership and the change-log row. Use the
   independent outing time zone. The outing's own window stays empty until a member enters one (A1.4).

Outcomes for each ordering, all required as tests:

| Race | First to commit | Result |
| --- | --- | --- |
| Regeneration vs anchor creation | regeneration deletes the uncommitted occurrence | creation finds no event: refused; no outing |
| | anchor creation | regeneration sees the anchor under its lock: the occurrence is committed, moved in place and flagged `moved`; never deleted |
| Direct leave vs anchor creation | the leave | creation finds no attendee row: refused |
| | anchor creation | the leave then succeeds. The outing stays and stays anchored (membership and attendance are independent); nothing is flagged |
| Event edit or cancel vs anchor creation | the edit | creation reads the new time under the lock, or is refused if cancelled |
| | anchor creation | the trigger finds the new outing and flags it |

### A1.4 The anchor's lifecycle, for every way an event can go away

**The foreign key.** `outing_anchors.event_id uuid references public.events (id) on delete set null`,
with `flag in ('moved', 'cancelled', 'removed')` or null, and a check that a row without an event id
must have the flag `removed`. `set null` is chosen over `restrict` for two reasons: the creator's
account-deletion cascade must go through (0012, 0027), and refusing a host's delete "because a plan is
attached" would tell the host that some attendee has a private outing. (Decided in the second review.)

**No silent detach.** A `before delete` trigger on `events` runs first, in the same transaction. For
each outing anchored to the row (locked in ascending id) it sets the anchor's flag to `removed`, writes the
change-log row, invalidates the outing's itineraries and notifies joined members. Only then does the
foreign key clear the pointer. So an outing never ends up with a null anchor and no flag: either it
was never anchored (both null), or it says its event was removed.

| How the event goes away | What happens to the event | What the outing shows |
| --- | --- | --- |
| Series regeneration | an anchored occurrence is committed (4.0 A1.4 rule d): never deleted; moved in place, or kept | `moved` when its time changed; nothing when it was kept |
| Host cancels, or cancelled below minimum, or the series ends | `status = 'cancelled'` (an update) | `cancelled` |
| Moderation removes it | `status = 'removed'` (an update) | `cancelled`. The reason is not shown to members |
| Owner deletes it (allowed today only when nobody else joined) | row deleted | `removed` |
| The host's account is deleted | their future events are cancelled first (`prepare_account_deletion`), then the profile cascade deletes the rows | `cancelled`, then `removed`. The cascade is never blocked by an outing |
| The outing owner's or the anchoring member's account is deleted | nothing: their attendee row cascades away on its own | unchanged. The anchor belongs to the outing, not to the member. The outing's own lifecycle for a deleted owner is §2 and §14, unchanged |

**Event access rules apply to everything derived from the anchor.** A later query through the
event's own RLS cannot hide a value that was already copied onto an outing or an itinerary. So
nothing event-derived is stored where a member can read it, and what is read is decided per member
at read time.

- **Storage.** `outing_anchors` has **no select grant for API roles** and no RLS policy that returns
  rows; a direct PostgREST read returns nothing. The `outings` row has no anchor column. Anchoring
  copies no event date, time, title or venue anywhere.
- **Reading.** `outing_anchor(p_outing)`, a definer RPC, is the only read path. For a joined member
  it always returns `{ anchored: true, flag }`. It adds `event_id`, and through it the event's
  current start, end, title and venue, **only when `can_view_event(event_id)` holds for the caller
  at that moment**. A member who cannot read the event gets the generic anchor and its flag and
  nothing else.
- **Saved itineraries.** A version stores the fixed stop as `{ kind: "anchor" }` with **no event id
  and no time**. The itinerary read RPC fills its start and end from the live event for a member
  who can read it; for a member who cannot, the stop is returned as "an event" with no time. The
  same rule applies to every earlier version, so losing access also hides it in versions saved
  while access existed. Itinerary tables have no direct select for API roles either (6.3).
- **What a member without access still sees:** the anchor flag and planning data the group authored,
  including the outing's window, shortlist, votes, stop details and order. The computed schedule,
  route and verdict details for an anchored version require current event access, including results
  for surrounding stops.
- **The outing's window is authored, not copied.** The form may offer the event's time as a starting
  value to a member who can read the event. Saving it is that member's choice to share a time with
  the group; nothing writes it automatically.
- The change-log payload for an anchor change is the flag only. The notification
  (`outing_anchor_changed`) carries the **outing's** title only.
- Account deletion keeps its guarantees: nothing about a deleted person is retained in the anchor
  row (`anchored_by` is `on delete set null`), the log payload or the notification.

**Atomicity and which ticket enforces what.**

| Invariant | Enforced by | Introduced in |
| --- | --- | --- |
| The flag is set in the same transaction as the event's time, venue or status change | `after update` trigger on `events` | 5.5 |
| The flag is set before a deleted event's pointer is cleared | `before delete` trigger on `events` + `on delete set null` on `outing_anchors` | 5.5 |
| An anchored occurrence is never deleted by regeneration | 4.0 A1.4 rule d, checked under the event lock | 4.5a declares the rule against a table that does not exist yet (it checks `to_regclass`); 5.5 adds the table and the two-connection proof |
| Itineraries anchored to a changed event are invalidated in that same transaction | the same trigger functions, replaced to add the invalidation statement after the outing lock | the ticket that creates the itinerary table (6.3). Until then the trigger has nothing to invalidate, and 5.5's tests say so |

### A1.5 Hard vetoes hold under the outing lock (5.3)

**Standing constraints and vetoes are different things.** A row in `outing_constraints` is something
a member tells the group ("vegetarian", "step-free"). It is shown beside every item and it does **not**
veto anything by itself: the system cannot judge whether a place meets it. An item is vetoed only by
that member's own `cant` vote on that item carrying a `constraint_kind`. The UI may prompt a member
with a standing constraint to review an item, but only their vote vetoes it.

**Eligibility, the same for both lock paths.** Evaluated under the outing row lock, from rows read
**after** the lock is granted: an item can be locked only if it belongs to this outing, has not been
removed, its place is still readable (§4), and no currently `joined` member has a veto vote on it.
Votes of members who are `removed` or `left` at that moment do not count, for or against.

- **Manual lock** (`lock_outing`): refuses a vetoed or otherwise ineligible item, for hosts too. A
  host cannot override a veto; that is what "veto instead of being outvoted" means.
- **Deadline lock** (`lock_due_outings`): ranks eligible items only. No eligible item, or a tie at the
  top: nothing is locked and hosts are told, as in §6.

**Every write that can change eligibility is serialized on the outing row, and the lock is always
taken first.**

- API roles have no direct write on any outing child table (§8). All writes go through RPCs whose
  first act is `findmaxxing_private.lock_outing_row(p_outing)`: it takes the outing row `for update`
  and records the outing's id in a transaction-local setting.
- **No child trigger takes the outing lock.** Revision 2 proposed a trigger on votes and constraints
  that locked the parent. On an update or delete the child row is already locked when a row trigger
  runs, so that would be child → outing, the reverse of every RPC. It is withdrawn.
- **The guard fails closed instead.** A `before insert or update or delete` trigger on each outing
  child table (members, items, votes, constraints, anchors, itinerary versions) takes no lock. It
  checks that this transaction has recorded the parent outing through `lock_outing_row`, and raises
  `outing:write_path` otherwise. It then refuses a vote or item change once the outing is `locked`.
  A direct write by the service role, a forgotten code path or a future migration is refused rather
  than left to race.
- **Cascades go through the same door.** Deleting an outing locks it first and so passes the guard.
  A member's account closure does not rely on the profile cascade: `prepare_account_deletion`, which
  already holds the user's account lock, calls an outing step that locks each of the user's outings
  in ascending id and removes or neutralizes their rows there (membership set to `left`, votes and
  constraints deleted, the log's actor cleared). The later cascade then has nothing to delete in a
  guarded table. Order: account → outing → child rows, as in 4.0 A1.9.
- The event-side triggers (material change, delete) call the same `lock_outing_row` for each
  anchoring outing in ascending id before they touch its anchor or itineraries.
- A standing-constraint change takes the same lock so the log order is true. It is allowed after a
  lock, since a person's limit is still a fact, is logged, and does not alter the locked decision.

| Race | First to commit | Result |
| --- | --- | --- |
| A veto vs a manual lock of that item | the veto | the lock re-reads votes under the outing lock and is refused |
| | the lock | the vote finds the outing `locked` and is refused; the member can ask a host to reopen (O-7) |
| A veto vs the deadline sweep | the veto | the sweep ranks without that item |
| | the sweep | the vote is refused as above |
| A veto withdrawn vs either lock | the withdrawal | the item is eligible again and may be locked |
| | the lock | the item was ineligible at lock time; a different item, or none, was locked |
| A member removed vs a lock | the removal | their veto no longer counts |
| | the lock | the decision stands; the removal is logged after it |

In no ordering can an item that was vetoed at the moment of locking be selected.

### A1.6 Required proof (added to §11)

Two PostgreSQL connections with controlled interleaving, as in 4.0 A1.6. Each ordering in the tables
above is its own assertion.

- Regeneration vs anchor creation; direct leave vs anchor creation; event edit vs anchor creation.
- A constraint-carrying vote, its withdrawal, and a member's removal, each racing the manual lock and
  racing the deadline lock.
- Lock order: with the event lock held by another connection, the material-change path waits and
  holds no outing lock; with an outing lock held, no outing RPC waits on an event lock.
- Event deletion with an existing anchor: owner delete, the host's account deletion (cascade goes
  through), and moderation removal. Each leaves the documented flag and never a null pointer without
  one.
- Account deletion of the outing owner and of the anchoring member with an anchor present.
- Access through the real API as a non-member, a removed member and a member who cannot read the
  event: no event field, private save, note or list name appears in the outing, the change log or a
  notification.
- Event change with no itinerary (flag only) and, from 6.3, with one (flag and invalidation in the
  same transaction).
- **Anchor privacy through the real API.** A joined member who never had access to the event, and a
  member whose access is revoked after an itinerary was saved: direct PostgREST reads of `outings`,
  `outing_anchors` and the itinerary tables, and both read RPCs, return no event id, title, venue,
  date or time, for the current version and for earlier ones. A member with access gets them.
- **Event delete racing an itinerary save.** Either order completes without a deadlock. Delete
  first: the save sees the `removed` flag. Save first: the delete then flags the outing and
  invalidates the new version in its own transaction.
- **The write-path guard.** A direct insert, update and delete on each child table as the service
  role is refused. The same write through its RPC succeeds. A member's account closure with votes,
  constraints and an anchor present completes, leaves no row of theirs, and blocks no other writer.
- Lock order: with a child row locked by another connection, an outing RPC waits holding only the
  outing lock; no trigger in the outing tables waits on an outing row.
- Each race test must fail when its guard (the lock, the re-read under lock, or the trigger) is
  removed.

### A1.8 Decisions on the open points

Revision 2 asked three questions. The second review answered them; they are part of the contract.

1. **`on delete set null` with an atomic `removed` flag**, preserving the account-deletion cascade
   (A1.4).
2. **Standing constraints inform the group; only a member's explicit veto on an item blocks locking**
   (A1.5). The veto applies to manual and deadline locks alike.
3. **Votes from removed or departed members stop counting** for future decisions (A1.5).

The revision 3 preflight answers the itinerary visibility question in A1.4. Members keep the group's authored planning data. See the [privacy contract](amendments-r3-codex-review.md#50-outings-and-the-63-itinerary-read-contract) for the required API tests.

## 2. Model

```
outings ──< outing_members ──< outing_votes >── outing_items
   │    ──< outing_invites                (hashed tokens)
   │    ──< outing_constraints            (member-declared hard limits)
   │    ──< outing_changes                (append-only log)
   │    ──  outing chat                   (conversation kind 'outing')
   └── anchor_event_id → events (4.0 occurrence, optional)
```

`outings`:
- `id`, `owner_id`, `title` (1–80), `note` (≤ 280, public to members);
- `time_zone` (IANA, required); `starts_local` / `ends_local` (optional plan window);
- `decision_deadline` (instant, optional);
- `status`: `draft` → `deciding` → `locked`; `cancelled` from any state;
- `locked_item_id`, `locked_at`, `locked_by`;
- `anchor_event_id` (nullable; set only by 5.5), `anchor_flag` (`null` / `moved` / `cancelled`);
- `created_at`, `updated_at`.

`outing_members(outing_id, user_id, role in ('host','member'), state in ('joined','removed','left'),
joined_at, removed_at, removed_by)`. The owner is a `host`; hosts can add hosts. Primary key on
`(outing_id, user_id)`. A `removed` row is kept so a removed person can't rejoin through an old invite.

## 3. Invites

- `outing_invites(id, outing_id, token_hash, created_by, created_at, expires_at, revoked_at, max_uses, uses)`.
- The token is 32 random bytes (base64url) shown once in the link. Only its SHA-256 is stored.
- **Shareable link (decision O-1):** multi-use. It expires after **7 days** by default (host can choose
  1–14 days) and is revocable. Total uses are capped at the member cap.
- **Member cap (decision O-2): 12 joined members** per outing.
- `claim_invite(token)`: authenticated only, via a definer RPC. It checks that the token exists, isn't
  revoked or expired, isn't over cap, the outing isn't cancelled or locked (O-3: no joining after lock),
  the claimer isn't `removed` from this outing, isn't blocked either way with any host, and isn't suspended
  or closing. Then it inserts a `joined` member and increments `uses`, under a lock on the outing row.
  Failures return one generic "This invite isn't valid any more", so a token can't be probed for its reason.

**Signed-out friends (5.4):** `/o/<token>` shows only the outing title, the inviter's display name and
"Sign in to join". No shortlist, members or votes are shown until claimed. **Identity is required before
voting.** After sign-up or sign-in the token is carried through the auth redirect, using the existing
`safeAuthNext`, and claimed once. The token is never logged; links get `Referrer-Policy: no-referrer`.

## 4. Shortlist items

`outing_items(id, outing_id, place_id, added_by, reason (≤ 140, written fresh), created_at, removed_at)`:
- unique `(outing_id, place_id)` among live items;
- **5 to 12 items** per outing (decision O-4: at least 2 to open voting, at most 12).

**What an item may reference (decision O-5): only places every current member can view: published,
`visibility = 'public'`.** Locals-only, followers-only, trusted, private and draft places (3.3) can't be
added. That is the simplest way to guarantee a member never learns of a place through the outing that
they couldn't see otherwise. Each item is re-checked at read time; a place that becomes hidden or removed
shows "No longer available" and can't win.

## 5. Adding from saves (3.1 not built yet)

- **5.2 copies only the place id.** "Add from my saves" lists the viewer's own saves and lists,
  owner-only as today. Adding creates an item with `place_id`, `added_by` and the `reason` the member
  types in the add dialog.
- **Never copied, now or after 3.1:** the source list name, the save's private note, personal tags,
  `recommended_by`, the source URL, the save status, or anything else 3.1 adds as "Only you". The
  database enforces this structurally: `outing_items` has no column that could hold those fields, and the
  add RPC takes only `(outing_id, place_id, reason)`.
- **Before 3.1 lands,** 5.2 works with today's saves and lists. After 3.1, the add dialog may *show*
  the user their own private note as a reminder (client-side, never sent). Required test: a private note
  and list name never appear in any outing response, notification, invite page or chat (§11).
- Members can also add from search (any public place), not only from saves.

## 6. Votes, constraints, deadline and lock (5.3)

- `outing_votes(outing_id, item_id, user_id, choice in ('yes','fine','cant'), constraint_kind null, updated_at)`.
  One **current** vote per member per item: primary key `(item_id, user_id)`, upserted. History goes to
  `outing_changes`.
- **Hard constraints veto instead of being outvoted.** A `cant` vote may carry a `constraint_kind`
  (`dietary`, `accessibility`, `budget`, `other`). A `cant` with a constraint **vetoes** the item: it can't
  win, whatever the counts. A plain `cant` counts against the item. Members can also declare standing
  constraints in `outing_constraints(outing_id, user_id, kind, note ≤ 140)`, visible to members, so
  others know before suggesting.
- **Visibility of votes (decision O-6):** members see each item's counts **and who voted what**. Open
  ballots fit friends planning together and make the veto accountable. These are the members' own
  votes, not a summary of friends' opinions about a place: no review text and no "friends liked this".
  Non-members see nothing. There are **no match scores** of any kind (founder decision).
- **Ranking:** vetoed items are excluded. The rest sort by `yes`, then `yes + fine`, then fewest `cant`,
  then earliest added. The tie-break is deterministic and shown ("tied; the host decides" when the top
  two are equal on the first three keys).
- **Lock:** a host locks manually, or at `decision_deadline` the service-only `lock_due_outings(p_now)`
  locks the top-ranked item. If the top two are tied, it notifies hosts to choose instead of guessing.
  Locking sets `status = 'locked'`, `locked_item_id`, `locked_at` and `locked_by`, under `select … for
  update` on the outing row. **Votes, item changes and claims all take the same lock and refuse when
  `locked`, so simultaneous edits can't replace a locked decision.**
- **Unlock (decision O-7):** a host can reopen it once, with a reason that is logged; the reason is shown
  to members.
- `outing_changes(id, outing_id, actor_id, kind, payload jsonb, at)`: append-only (a trigger blocks
  update/delete). It records add/remove item, vote, constraint, lock, unlock, member removed/left,
  invite revoked, anchor flag. Members can read it.

## 7. Anchor to an event occurrence (5.5)

- `start_outing_from_event(p_event)`: the caller must be **going** to that occurrence (`event_attendees`,
  4.0 D-B). It creates an outing with `anchor_event_id = p_event`, `time_zone` = the occurrence's
  `time_zone` (4.0 §4), and the window starting at the occurrence's end (default). The fixed start time
  becomes a locked constraint for planning (6.0 §4).
- Occurrence ids are stable (4.0 D-A). Occurrences with participants are never regenerated (4.0 §8).
- **Material change (4.0 §9):** when the anchored occurrence's time or venue changes, set
  `anchor_flag = 'moved'`; when it's cancelled, set `'cancelled'`. Both happen in the same transaction as
  the event update (a trigger on `events`), and members are notified (`outing_anchor_changed`). The
  outing isn't deleted. Itineraries anchored to it are invalidated (6.0 §5).
- The outing never RSVPs anyone to the event. Membership and attendance are independent.

## 8. RLS and direct-API attack cases

Every table: RLS on, **no direct writes for API roles**; writes only through definer RPCs that call
`is_outing_member(outing, auth.uid())` (`joined` state) and, where needed, `is_outing_host`.

| Table | Read |
| --- | --- |
| `outings` | Joined members, plus title-only through the invite landing RPC (§3). |
| `outing_members` | Joined members see joined members and roles. A removed person sees nothing. |
| `outing_items`, `outing_votes`, `outing_constraints`, `outing_changes` | Joined members only. |
| `outing_invites` | Hosts only, and never `token_hash` (column privileges). |

Attack cases the tests must cover (direct PostgREST calls as a real user):
- a non-member reads any outing table;
- a removed member reads after removal (page, API, chat, notifications);
- a member votes on another outing's item;
- forging `user_id` on a vote;
- adding a private, locals or draft place;
- adding when locked;
- claiming an expired, revoked or over-cap invite, or as a removed member;
- guessing tokens (generic failure, rate-limited claims);
- reading `token_hash`;
- a blocked user claiming the invite of someone who blocked them;
- reading another user's saves through an outing.

## 9. Chat and notifications

- **Outing chat (decision O-8):** reuse messaging with a new conversation kind `'outing'` and an
  `outing_id`. This relaxes 0020's group/event check in a new migration. Membership syncs from
  `outing_members` the way 0020 syncs event attendees. This is "friends discuss plans among themselves".
- **Notifications** (new types added to `check_notification_settings`):
  - `outing_invited` (when a member adds a known user);
  - `outing_deadline_soon` (2 hours before);
  - `outing_locked`;
  - `outing_tie` (hosts);
  - `outing_anchor_changed`;
  - `outing_removed` (to the removed person, with no content).
  All go through `notify()` (blocks, mutes, quiet hours, daily push cap) with dedupe keys per outing and
  event. Labels carry the outing title and never a place's private context.
- **Realtime:** polling for v1 (decision O-9: every 15 s while the outing page is visible, paused when
  hidden). Supabase Realtime later if needed.

## 10. Native (8.1c–d)

The same RPCs, with no direct table access. Deep link `findmaxxing://o/<token>`, which also handles a cold
launch. After sign-in, land on the outing. An expired link shows the generic message.

## 11. Test plan

- **Concurrency (two PostgreSQL connections, `tests/helpers/postgres.ts`):**
  - lock vs vote;
  - lock vs add item;
  - two hosts locking at once (one winner, one no-op);
  - the deadline sweep vs a manual lock;
  - claim vs revoke;
  - two claims for the last member slot;
  - removal vs that member's vote;
  - the anchor event update vs outing creation from it.
- **RLS and attack cases:** every row in §8, as anon, a non-member, a member, a host, a removed member,
  a moderator, and a blocked user.
- **Privacy promise:**
  - a private note, list name, tag (after 3.1) or draft place never appears in an outing response, change
    log, notification, invite landing, chat sync or share;
  - an item's place becoming non-public hides it from members who lose access.
- **Logic:** ranking and tie-break; veto beats counts; one current vote; append-only log; DST for
  deadlines (first-instant rule); invite expiry on a frozen clock; anchor moved/cancelled flags.
- **Real code paths:** server actions and RPCs from web; native RPC calls in 8.1c; demo twins at parity.

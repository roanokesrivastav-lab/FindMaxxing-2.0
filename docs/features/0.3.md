# 0.3 Pilot flags and seed

Built 2026-11-05 under [beta-build-rules.md](../beta-build-rules.md). Ticket: roadmap-80.md §4, M0 "0.3".

## Contract

- **Objective:** pilot feature flags in the existing registry that can never be turned on by `all`,
  enabled explicitly in demo and test configuration; demo seed accounts for host, participant, outsider
  and moderator; seed records marked pilot vs fictional.
- **Out of scope:** any pilot feature itself; migrations (none needed); production configuration.
- **Required tests (from the ticket):** existing flags unchanged, `all` excludes pilot flags, explicit
  listing enables them, required-key checks still apply.

**Dependency note.** 0.3 lists `Needs: 0.1`. On this branch 0.1a is done and verified (security-audit-repair.md
"Batch 1 - 0.1a"), so the codebase compiles and checks pass. 0.1b (ad beacon and billing) is not started and
touches nothing 0.3 uses (flags, seed, config). 0.3 was built on that basis; nothing in it depends on 0.1b.

## Changes

- `src/lib/config.ts`: `PILOT_FEATURES` (one per milestone: `pilotFoundation` M1, `pilotExplore` M2,
  `pilotLibrary` M3, `pilotEvents` M4, `pilotOutings` M5, `pilotItinerary` M6, `pilotLocal` M7) in the
  same registry and the same `featureEnabled()`. Pilot flags are on only when named or when the
  explicit token `pilot` is listed; `all` never enables them. Required-key checks apply to every flag
  as before. `pilotFlags()` resolves availability on the server for passing to client components as a
  prop. `FEATURES` and its behaviour are unchanged; the type `Feature` now covers both lists.
- **Demo and test configuration (not code defaults):**
  - `.env.development` (new, committed): `NEXT_PUBLIC_FEATURES=pilot`. `next dev` loads it; `next build`
    and `next start` never do, so production cannot pick it up. `.gitignore` allows this one file.
  - `scripts/lib/demo-server.mjs`: appends `pilot` to whatever `NEXT_PUBLIC_FEATURES` the caller passes
    (e2e, e2e-features, a11y, measure-images).
  - `vitest.config.mts`: `NEXT_PUBLIC_FEATURES: "pilot"`; every existing flag stays off unless a test
    lists it.
- `src/lib/seed/seed-data.ts`:
  - `SeedOrigin` (`fictional` | `pilot`) and `seedOrigin()`, with optional `origin` on users, places and
    events. Unmarked means fictional; all current data is fictional.
  - Four fictional role accounts: `hana_host` (host@example.com), `pat_participant`
    (participant@example.com), `olu_outsider` (outsider@example.com) and `mo_moderator`
    (moderator@example.com, added to `SEED_MODERATORS`). Credentials appear only in this file
    (`SEED_ROLE_ACCOUNTS`, all `DEMO_PASSWORD`).
  - A host event, "Thursday pickup basketball" (capacity 10), joined by the participant. The outsider
    has no follows, saves or events.
- `tests/pilot-flags.test.ts` (new, 9 tests). `tests/moderation.test.ts`: three assertions that pinned
  `sam_k` as the only seeded moderator now use `SEED_MODERATORS` (intent unchanged).
- README "Feature flags": pilot flags, the `pilot` token, demo/test configuration, role accounts.

Migrations: **none** (Core block 0042–0049 untouched). New dependencies: **none**.

## Could not verify / limits

- No pilot feature exists yet, so no UI currently reads a pilot flag (1.1's `/dev/ui` page is the first).
- The `fictional`/`pilot` marker lives in the seed source only; it is not stored in the database (that
  would need a Core migration). Generated SQL and the demo store carry no origin column.
- Existing local demo stores (`.data/demo-store.json`) were created from the old seed and will not
  contain the role accounts. Start a fresh store (delete the file, or `FINDMAXXING_DEMO_FRESH=1`) to see
  them. No store migration was added, because adding accounts to someone's existing store would be
  surprising.
- Hosted staging was not touched; whether staging's `NEXT_PUBLIC_FEATURES` contains `all` is unknown, and
  by design it would not matter.
- **Tooling note for the migration blocks:** both test harnesses apply migrations in filename order, so
  gaps between blocks are fine (no contiguity required). But Supabase `db push` normally refuses a local
  migration numbered below the latest one already applied remotely. If 0041 (0.1b) is applied after any
  0042+ migration, it would need `supabase db push --include-all`. Recorded here, not changed.

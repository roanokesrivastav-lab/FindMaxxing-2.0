## Non-negotiables (the places this goes wrong)
1. **One lock order.** Every seat-changing path takes `select … from events where id = p_event for update` first,
   same as the existing trigger and `reserve_ticket`. Participant-row locks come second. Never the reverse (deadlock).
2. **One capacity definition.** `seats_taken = going + live offers + live pending paid holds`, "live" meaning
   compared against `clock_timestamp()`, not a sweep. Implement it once as a function and use it in the join trigger,
   `join_event`, `accept_offer`, `offer_next`, `reserve_ticket` and the capacity-edit guard. No second copy of the math.
3. **`event_attendees` still means exactly "going".** Invariant by trigger: never both a going row and a participant
   row for the same user and event.
4. **Fall-back DST.** The generator must NOT use bare `at time zone`; resolve the ambiguous hour to the *first*
   instant (D-G) and add a shared test vector that runs against both the SQL and `src/lib/utils/timezone.ts`.
5. **Service-driven changes notify explicitly** (null actor). `notify_on_event_change` is silent without
   `auth.uid()`. Use the dedupe keys in §9 so a re-run sends one notification per offer.
6. **Definer RPC hygiene:** `security definer`, `set search_path = public`, refuse suspended or closing accounts like
   `reserve_ticket`, no broad grants. Add new notification types to `check_notification_settings` without breaking
   existing settings.
7. **Legacy writes:** switch web `repository.ts` join/leave to the RPCs (demo twin at parity). Add a source-check test
   that no direct `event_attendees` writes remain in web actions. Phase 2 revokes the authenticated insert/delete
   policies on `event_attendees` in the same release, as D-I recommends.
8. **Demo repository twins** must implement every new RPC with the same behaviour, or demo mode drifts from prod.

# Personalized recommendations plan

## 1. Current state

- `0018_recommendations.sql`: authenticated, `SECURITY INVOKER` functions `recommend_places` / `recommend_events`; existing RLS filters visibility.
- Places: followed creator +4; any followed rating ≥4 +3; any tag shared with own save/rating ≥4 +3; each interest tag +2; joined-event category +1.
- Place bonuses: `2*exp(-distance_m/3000)`; community source +1.5; `1.5/(1+places.save_count)`.
- Events: own saved venue +4; followed host +4; any followed non-host attendee +2; each interest tag +2; usual joined-event weekday +1.
- Event bonuses: `1.5*exp(-max(seconds_until_start,0)/259200)`; same distance bonus; fewer than five attendees +0.5.
- Both require a personal signal; exclude own creations and already saved/rated places or joined events. Event cutoff permits end/start up to one hour ago.
- Scores round to 0.001, ties use ID; strongest signal explains recommendation; RPC limit 1–50, default 12.
- `recommendDemoPlaces` / `recommendDemoEvents` in `src/lib/data/demo/recommend.ts` mirror SQL weights, eligibility, explanations and ordering; preserve parity with every change.
- `forYouPlaces` / `forYouEvents` in `src/server/recommendations/index.ts` require sign-in and the `recommendations` flag, retrieving 12 candidates.
- Optional `rerankPlaces` sends own interests, up to 20 saved names and candidate metadata to Claude; four-second request timeout, caught failures return rules. `applyOrder` drops unknown/duplicate IDs and appends omitted candidates.
- Gaps: no exposure history, explicit negative feedback, category-specific taste vectors, learning, set-level diversity, category travel scales, opening-hours or party context; cold users can receive nothing.
- Low ratings only exclude that place; boosts for lesser-known places are not diversity control. Event joins do not prove attendance; fixed New York weekday logic limits expansion.

## 2. Data we must start collecting now

Propose **one append-only table**, `public.recommendation_interactions`, holding both impressions and actions. This is a design contract, not an applied migration. Existing `saved_places`, `place_ratings` and `event_attendees` remain authoritative current state; history must not replace them.

| Column | Exact proposed type / constraint | Meaning |
|---|---|---|
| `id` | `uuid PRIMARY KEY DEFAULT gen_random_uuid()` | Row identity; impression rows supply attribution IDs. |
| `user_id` | `uuid NOT NULL REFERENCES public.profiles(id) ON DELETE CASCADE` | Derived from authenticated session, never caller-selected. |
| `client_event_id` | `uuid NOT NULL`, unique with `user_id` | Stable retry key, including server-side mutation retries. |
| `action` | `text NOT NULL CHECK IN ('impression','view','save','unsave','rate','join','leave','hide','unhide')` | `rate` is place-only; `save/unsave` place-only; `join/leave` event-only. |
| `place_id` | `uuid NULL REFERENCES public.places(id) ON DELETE CASCADE` | Exactly one of place/event ID must be non-null. |
| `event_id` | `uuid NULL REFERENCES public.events(id) ON DELETE CASCADE` | Same XOR constraint; no unvalidated generic item ID. |
| `occurred_at` | `timestamptz NOT NULL DEFAULT now()` | Server time, authoritative for labels and ordering. |
| `client_at` | `timestamptz NULL` | Diagnostic only; reject beyond ±5 minutes of receipt. |
| `request_id` | `uuid NULL` | Recommendation response identity; required for recommendation impressions. |
| `session_id` | `uuid NULL` | Random session token, rotated daily; no cross-device fingerprint. |
| `impression_id` | `uuid NULL REFERENCES public.recommendation_interactions(id) ON DELETE SET NULL` | Optional parent exposure for an action; null on impressions. |
| `surface` | `text NOT NULL CHECK IN ('for_you_places','for_you_events','explore_list','explore_map','search','place_detail','event_detail','saved_list','direct')` | Where the action happened; parent impression identifies originating rail. |
| `list_position` | `smallint NULL CHECK (list_position BETWEEN 1 AND 500)` | One-based final displayed position; required on list impressions, null for direct detail/map actions. |
| `category_slug` | `text NOT NULL REFERENCES public.categories(slug)` | Server-derived category snapshot at action time. |
| `rating_value` | `smallint NULL CHECK (rating_value BETWEEN 1 AND 5)` | Non-null iff action = `rate`; never store rating-note text. |
| `policy_version` | `text NULL CHECK (char_length(policy_version) <= 80)` | Required for recommendation impressions; e.g. `rules-v1`, including rerank variant. |
| `experiment_key`, `variant` | each `text NULL CHECK (char_length(...) <= 80)` | Both set or both null; server-assigned. |
| `candidate_source` | `text NULL CHECK IN ('rules','fallback','content','semantic','item_cf','taste_match','exploration')` | Required for recommendation impressions; primary retrieval source. |
| `selection_probability` | `double precision NULL CHECK (selection_probability > 0 AND selection_probability <= 1)` | Joint randomized item-and-position selection probability; null if not known. |
| `features` | `jsonb NOT NULL DEFAULT '{}'`, object only, `pg_column_size <= 2048` | Versioned, server-authored numeric/categorical snapshot, allowlisted below. |

Allowlisted `features`: `schema_version`, `rule_score`, `content_score`, `cf_score`, `distance_bucket` (`<1km/1–3/3–10/10–30/>30/unknown`), `local_hour`, `local_dow`, `timezone`, `open_state` (`open/closed/unknown`), `party_mode` (`solo/group/unknown`), `hours_to_start`, `available_capacity`, `eligible_count`, `reason_kind`, `retrieval_version`, `exploration_pool_size`, `exploration_step`, `slot_probability`. Missing is null/absent, never zero. No coordinates, raw query, names, free-text URLs, or arbitrary payloads. Snapshot only features actually used; add learned-ranker features via an explicit versioned allowlist later.

**Write and read contract:**

- Enable RLS. Grant authenticated users `SELECT` only with `USING (user_id = auth.uid())`; no anonymous access, admin-wide browse policy, or direct client `INSERT/UPDATE/DELETE` grants. Service role is trusted infrastructure, never exposed to browser code.
- Proposed `record_recommendation_interaction(...)` RPC: tightly scoped `SECURITY DEFINER`, fixed `search_path`, execute only for authenticated; derive user, category and timestamps; enforce consent, rate limits, target visibility via `can_view_place` / `can_view_event`, action/type constraints and deduplication. Accept no user ID parameter.
- Attach existing `block_suspended_writes()` to new signed-in writes; check `account_is_closing(auth.uid())` and use the existing `account_close:` advisory lock. Add a matching owner-only INSERT policy as defense in depth even though direct inserts remain revoked.
- Enforce parent attribution in the writer: parent is `impression`, same user and exact same item, precedes action, within the attribution window. Resolve only IDs the caller owns; reject cross-user parents without revealing whether they exist.
- Client RPC records only `impression/view/hide/unhide`. Record `save/unsave/rate/join/leave` through trusted hooks after successful canonical mutations, preferably DB transaction hooks; include webhook-confirmed paid joins, not checkout clicks. Derive owner from the mutated row for service callbacks, and apply the same consent/closing-account checks. Failed saves/joins emit no positive signal.
- Pass server-issued signed response metadata through the card, verifying request, item, position, policy and context on impression ingestion. This prevents fabricated ranking metadata; viewport visibility itself is a client observation, so bound rates and filter bots.
- Impression = ≥50% of card visible for ≥1 continuous second in a visible tab; once per `(user_id, request_id, item)` even after carousel scroll/remount. A new list response creates a new request. `view` = opened detail page, not hover/prefetch. Out-of-order actions remain unattributed unless a valid parent arrives; do not drop the successful action.

**Indexes:** unique `(user_id, client_event_id)`; `(user_id, occurred_at DESC)`; `(occurred_at)` for retention; `(impression_id)` where non-null; `(place_id, occurred_at DESC)` / `(event_id, occurred_at DESC)` where non-null. Partial unique indexes on `(user_id, request_id, place_id)` and `(user_id, request_id, event_id)` where `action='impression' AND request_id IS NOT NULL` enforce exposure deduplication. No GIN index on `features` initially.

**Consent, retention and deletion:** propose `profiles.recommendation_history_enabled boolean NOT NULL DEFAULT false`; explain this separately from `analytics_opt_out`. Without opt-in, use explicit current interests/saves/ratings under existing rules and collect no recommendation history. Before shared learning, add separate `profiles.recommendation_shared_training_enabled boolean NOT NULL DEFAULT false`; history consent alone does not authorize pooled training. Purge raw recommendation history at 180 days using a new service-only retention job. Keep durable `hide/unhide` state separately in a future owner-only `recommendation_feedback` table (same user/item FKs and XOR check), so retention never silently unhides an item. History reset clears history and derived taste state; unhide is explicit. Until that table exists, do not ship persistent hide UI.

`auth.users → profiles → recommendation_interactions` cascades on account deletion, as in `0012_account_deletion.sql`; item deletion also removes its history. Integrate with `prepare_account_deletion` / `account_deletion_jobs` from `0027_account_deletion_lifecycle.sql`: reject new writes once closing starts, invalidate caches immediately, and delete user profiles, comparisons, feedback and training exports. Later derived tables need cascading FKs too; external artifacts need retryable purge tracking before deletion completes. Rebuild affected shared aggregates/models from permitted remaining data; do not retain raw training exports indefinitely.

**Why not `analytics_events`:** `0015_analytics.sql` deliberately stores a salted `analytics_actor` hash, no user FK, admin-only reads, opt-out and 180-day retention. It records coarse actions but lacks recommendation request, impression, position and attribution semantics. This is pseudonymous rather than irreversibly anonymous: a privileged actor function exists, but reverse-mapping it would defeat the designed boundary. Do not repurpose `track_event`, change anonymous analytics, or backfill personalized history by joining hashed actors to profiles.

## 3. Staged roadmap tied to user counts

Counts are checkpoints, not evidence that an algorithm will work. Here “active” means a signed-in person with ≥1 discovery session in the last 28 days, within one city. Advance by category coverage and outcome volume; sparse categories keep the earlier fallback. Effort: **S** = one focused coding session, **M** = several sessions, **L** = a multi-week project including experiments. All numerical gates below are proposed starting targets, not research-established sample-size guarantees.

| Stage | Algorithm and why now | Inputs | Execution / effort | Good enough to move on |
|---|---|---|---|---|
| **0 users** | Existing rule scoring, plus explicit cold-start fallback and instrumentation. No collaborative signal exists. | `profile_interests`, own saves/ratings, visible followed activity, taxonomy, distance/time. | `recommend_places` / `recommend_events` in Postgres; demo twin; server diversity. **S** for fallback; **M** for logging end to end. | Permission and parity tests pass; opted-in QA actions have correct exposure attribution; all eligible cold users get useful results or an honest empty state. |
| **First beta, ~50–200** | Category-specific content profiles; small pairwise-rating pilot. One person's history is useful even with no neighbors. | Own interactions + item tags/text; explicit interests; same-category comparisons. | On-demand SQL weighted tags first; nightly private profile refresh as needed; small Bradley–Terry fit job. **M** each. | ≥30 users have ≥5 meaningful actions in at least one category; ≥95% of instrumented QA exposures/actions reconcile; weekly reviews show understandable suggestions; measured outcomes do not clearly regress. |
| **Late beta / ~500+ active in one city** | pgvector similarity + semantic search; item-item implicit CF only where co-occurrence is dense. Embeddings solve text mismatch without needing many users; CF discovers connections tags miss. | Public listing text; private own profile for own retrieval; shared CF uses public-event joins and public high ratings only. | Batch embedding worker → Postgres pgvector; nightly item-neighbor job → Postgres lookup. **M** embeddings, **M/L** CF. | Curated semantic query benchmark improves; eligible ANN recall ≥0.95 versus exact search if ANN enabled; CF has ≥10 distinct co-engagers per pair and covers ≥30% of active users; temporal Recall@50 improves ≥5% relative over content-only. |
| **~500+, optional dense-category pilot** | User-user taste match, kept separate from follows. Needs overlapping ratings, not just user count. | Public `place_ratings` on public places; minimum overlap; no private saves/comparisons. | Nightly category-scoped nearest-neighbor job; private neighbor cache and viewer-safe aggregate RPC. **M**. | ≥5 overlapping ratings per neighbor; ≥5 qualified neighbors rated candidate; useful coverage ≥20% of pilot users; uncertainty-calibrated explanation judged useful. Otherwise omit this feature. |
| **Thousands active** | Two-stage retrieval → regularized logistic regression; then LightGBM only if nonlinear gains justify it. Keep rules/content for sparse users and new items. | Eligible candidates; exposure-time public/context features; consented public rating/join outcomes. Own private taste remains an owner-only serving adjustment. | Retrieve in Postgres; train nightly/weekly in scheduled worker; logistic coefficients served in Next.js; later small versioned LightGBM inference service. **L**. | Start logistic experiment after ≥20k mature exposed examples and ≥1k public positive outcomes per task; require temporal NDCG@12 improvement and powered online test. Consider trees after ~100k examples/5k positives per task, only if they beat logistic reliably. |

**Rule baseline and cold start.** Keep current scoring as the control policy. When personal signals cannot fill 12 slots, backfill visible published items matching explicit category/city/date filters using `2*distance_decay + 1*quality + 0.5*freshness`; quality = `(rating_count/(rating_count+10))*(rating_avg/5)` for places, zero for unrated/new items. Freshness = `exp(-age_days/30)` for places, event urgency from §4. Use MMR and explain fallback as “Explore nearby,” never “Based on your taste.” Preserve exclusion of already saved/rated/joined items on discovery rails; revisit suggestions belong on a separate surface. Keep Claude reranking off for initial experiments to establish a cheap, deterministic baseline; it cannot recover candidates outside the existing shortlist.

**Content-based category taste.** Proposed private cache `user_category_taste(user_id, category_slug, profile_version, tag_weights jsonb, positive_count, updated_at)` with PK `(user_id, category_slug)` and cascading profile FK. Compute a separate normalized tag vector for each category; coffee behavior must not set sports preferences. Within-category contributions start at save +3, rating `2*(score-3)` (−4…+4), join +4, qualified detail view +0.25 capped once/item/day, impression 0; multiply by `exp(-age_days/90)`. Use latest current save/rating/join state, not every retry: unsave/leave retract the earlier contribution and are not automatic dislike. Hide excludes that item and contributes −2 to its tags; unhide removes that negative. Cap total positive evidence from one item at 6. Share an event's category evidence with places in that category at half weight, because intent to attend is weaker than satisfaction.

Split evidence evenly over an item's tags; combine positive centroid cosine similarity and a bounded negative-tag penalty. Shrink observed taste toward matching explicit `profile_interests` with `alpha=n/(n+5)`, where n is distinct meaningful items in that category. No matching interests/history means neutral profile and fallback. Mix normalized content/rule scores initially 30/70 after ≥3 meaningful items, up to 60/40 after ≥10; persist version and effective sample size. Do not add raw cosine to unbounded rule scores. Later replace tag-only positive centroids with text-embedding centroids; retain interpretable tags for explanations.

**Beli-style pairwise ratings: choose regularized Bradley–Terry.** For each user and category, fit latent item utilities with `P(A preferred to B)=sigmoid(theta_A-theta_B)` plus an L2 prior centered at zero. This provides probabilities, allows batch refitting after edits and avoids Elo's dependence on comparison order and a hand-tuned update rate. Sparse/disconnected comparisons still need shrinkage; do not present precise scores for unconnected items. This is a proposed design inspired by pairwise ranking, not a claim about Beli's proprietary algorithm. Standard reference: [Turner & Firth, Bradley–Terry Models](https://www.jstatsoft.org/article/view/v048i09).

Proposed private `place_comparisons(id uuid PK, user_id uuid FK profiles CASCADE, category_slug text FK categories, place_a_id uuid FK places CASCADE, place_b_id uuid FK places CASCADE, winner_place_id uuid FK places CASCADE, created_at timestamptz, updated_at timestamptz)`. Canonicalize A/B order, require A≠B, winner in {A,B}, both places visible and in the same category; unique `(user_id, place_a_id, place_b_id)`. Owner-only RLS, validated RPC, no public leaderboard. Offer skip/“haven't visited” without a preference row; begin after three explicitly visited/rated places, never infer a visit from a save. Ask 1–3 comparisons per new rating against already compared nearby ranks; show “not enough comparisons” until ≥5 edges connect the displayed items. Keep existing 1–5 `place_ratings` intact. Train from latest decisions, report private relative order, and transfer preferred-item tags into that user's category profile. Pairwise output is not a cross-user 5-star rating. Events can eventually ask about experienced host/series, rather than rank expired event IDs.

**Text embeddings and semantic search.** Batch-embed `places.name/description/local_tip`, category and tag labels; events use `title/description`, tags and public venue description. Proposed `place_embeddings(place_id PK/FK CASCADE, embedding vector(d), model_version, content_hash, updated_at)` and equivalent `event_embeddings`; d is fixed by the selected model. Re-embed only changed content; expire event entries after the event. Start with public listings only; owner/private taste vectors stay in trusted storage. Query “quiet study spot with outlets” against text embeddings, blend with existing lexical discovery using Reciprocal Rank Fusion, then enforce category/geography/time. Start exact cosine search within the eligible city/category; add HNSW only after measured latency requires it. Approximate filtering can underfill results, so verify recall against exact eligible search and use iterative scans/overfetch with an exact fallback. [pgvector documentation](https://github.com/pgvector/pgvector) describes exact search, HNSW and filtered iterative scans. A model API may encode public item text; use a local encoder for sensitive query text or get separate external-processing consent.

**Item-item CF on implicit feedback.** Standard name: [item-based collaborative filtering](https://files.grouplens.org/papers/www10_sarwar.pdf). For shared models, construct binary user-item positives from public-place ratings ≥4 and joins to publicly visible events, with one contribution per user/item and 90-day decay. Use cosine co-occurrence shrunk by `n_ij/(n_ij+20)`; require n_ij≥10 distinct contributors, store top 50 neighbors per item in a service-only `item_neighbors` cache. Aggregate event history to venue/host/series before computing neighbors because event IDs expire. Retract leaves, rating changes and deleted/visibility-restricted items during rebuild. A user's own saves may select which neighbor lists to consult privately, but other users' saves, views, hides and impressions never construct shared similarity. If this permitted graph is too sparse, remain content-based; no workaround via service-role access to private saves.

**User-user taste match.** Use Pearson correlation on co-rated public places within a category, shrink by overlap/(overlap+10), discard nonpositive correlations, and keep top 20 qualified neighbors. Prediction `X = viewer_mean + weighted_mean(neighbor_rating - neighbor_mean)` is clamped to 1–5, shrunk toward the category prior and displayed to one decimal. “People with your taste rate this X” requires ≥5 contributing neighbors, ≥5 co-ratings with each, and a visible rating on the candidate; otherwise show no number. Return only aggregate X/count, not identities or a percentage “match.” Cold users cannot receive a credible taste-match claim. Private pairwise utility scores are neither public ratings nor directly comparable between users.

**Two-stage retrieval and learned ranking.** Merge up to 50 rules + 50 content/vector + 50 item-CF + 25 social/taste-match + 25 exploration candidates; deduplicate to ≤200, enforce authorization and availability, score, then diversify to 12. Raise the current 12-candidate server shortlist before expecting reranking gains. Train separate place and event logistic heads with regularization and calibrated probabilities; place public label = new rating ≥4 within seven days, event label = successful join within its allowed window. Exposed rows with mature windows and no outcome are weak negatives, not dislikes. Exclude ineligible/cancelled periods, account closures and automated activity; private save/view/hide histories and derived private features are excluded from shared training. Use public listing/category/context features and permitted public co-occurrence; combine predictions with the owner's private content score at serving time. Save outcomes remain an evaluation target, not shared training labels under this privacy contract.

Try [LightGBM gradient-boosted decision trees](https://www.microsoft.com/en-us/research/project/lightgbm/) only after logistic plateaus; later LambdaMART ranking can group examples by recommendation request when enough requests have multiple labeled candidates. Preserve the same retrieval/control, immutable model/feature versions, missing-value behavior and rollback to rules on timeout. Do not compare uncalibrated place and event probabilities as if their actions had equal value. Keep separate rails initially. A scheduled training worker plus Postgres is sufficient until inference latency/operations justify an external service; no real-time feature platform is required.

## 4. Events specifically

An event often expires before it collects enough interactions. Transfer preference through `events.creator_id` (host), `place_id` (venue), `category_slug`, `event_tags`, and a proposed stable recurring-series identity. Never require an event itself to have prior joins before it can appear. Existing `event_attendees` is RSVP state, not confirmed attendance or enjoyment.

Proposed initial score, replacing rather than stacking on §1 event rules; these are tunable hypotheses:

| Signal | Weight / definition | Evidence |
|---|---|---|
| Recurring series | +5 × affinity in [0,1] | Add `event_series(id, creator_id, title)` and nullable `events.series_id` with ownership validation; affinity starts at min(prior retained joins/3,1). No series inference from similar titles. |
| Venue | +4 × affinity | 1 for own currently saved or rated ≥4 venue; otherwise min(prior retained joins there/3,1); own rating ≤2 gives 0. |
| Host | +3 × affinity | 1 if followed; otherwise min(prior retained joins to that host/3,1). Exclude self-hosting. |
| Category / tags | +4 × normalized category fit | §3 content profile, falling back to matching-interest fraction; unknown = neutral 0. |
| Followed people attending | +2 maximum | 1 point each for up to two followed non-host attendees; not all attendees are friends. Only currently visible attendance counts. |
| Timing fit | +1 maximum | Smoothed weekday/time-block preference with ≥3 prior joins, or explicit requested time window. |
| Time to start | `+1.5*exp(-hours_until_start/72)` | Future eligible events; cap at 1.5. Keep a separate “this week” view so urgency cannot erase advance planning. |
| Travel | `+2*exp(-distance_m/d_category)` | Category-dependent scale from §5; missing location = 0, not a penalty. |
| Small/new event exploration | +0.5 maximum | Under five attendees, including zero; exploration slot can surface it without historical personal evidence. |

Cap **series + venue + host together at 8** to avoid triple-counting the same repeated meetup. A retained join means joined without subsequently leaving/cancellation; use the user's own 180-day history, decayed with a 60-day time constant. Attendance satisfaction would be stronger but needs an explicit post-event check-in/rating feature; do not invent that observation. Leaves retract positive affinity; repeated hides of one series can reduce that user's series preference, but a single scheduling conflict must not imply dislike of a sport.

Eligibility happens **before scoring**: published, viewer-visible, not hidden by this user, not self-hosted/already joined, within requested geography/time and with remaining capacity. Default new-join rail requires `starts_at > now()`; this intentionally removes the existing one-hour grace window. Only allow in-progress drop-in events later with an explicit host-set join cutoff; absent `ends_at` must not mean indefinitely ongoing. Recheck capacity, cancellation and permissions at join time because ranking cannot reserve a seat. For paid events (`price_cents`, `currency`, `tickets`), recommend only when purchase is available and record `join` after confirmed admission; never treat checkout creation as a join.

Refresh event eligibility on every request and invalidate cached lists on cancellation/capacity/visibility changes; cached affinity can refresh nightly. Resolve time in the venue/city's IANA timezone, with America/New_York only as the current Columbus default. `event_series` visibility and embeddings must reveal no more than its visible instances. Keep at most one occurrence per series in a 12-card discovery rail unless the user asks to compare dates.

## 5. Context signals

Use explicit session intent before inferred habits. Context adjusts relevance, never authorization: nearby coordinates do not grant `is_local(city)` access. `distance_m` is straight-line distance, not travel time; label it honestly. Avoid persisting exact user location; compute distance transiently and log only a bucket.

| Category / intent | Starting distance scale d in `exp(-distance_m/d)` | Time of day / weekday | Open-now importance | Solo / group |
|---|---|---|---|---|
| Coffee / studying | 1.5 km | Morning/afternoon; session length matters more than weekday | High for “go now”; require enough remaining open time when known | Quiet/seating/outlets tags for solo; table-size/conversation tags for group |
| Food | 3 km | Meal windows, optionally weekday lunch vs weekend dinner | High for immediate intent; future plans use requested time | Group seating and price constraints if explicitly supplied |
| Nightlife | 5 km | Evening/weekend; venue-local date across midnight | High; after-midnight schedules need previous-day intervals | Explicit group intent; never infer alcohol preference from late browsing |
| Pickup sports | 5 km | Event start and travel buffer dominate | Court/venue hours matter, but event eligibility is primary | Solo can mean seeking teammates; do not penalize a solo user for a team event |
| Outdoors | 15 km | Daylight and requested date; weekend preference weak initially | Trail access/closure matters; absent information remains unknown | Solo/group difficulty or facilities only from explicit preferences/tags |

These are product labels to map to actual `categories.slug` values during implementation, not proposed replacement taxonomy slugs. Let users set a radius; use a hard radius only when explicitly requested and a soft decay otherwise. At beta, context contributes at most 20% of normalized score so a weak timing inference cannot overwhelm strong taste.

Opening hours, reliable IANA timezone and party-mode metadata are not present in the inspected core definitions; add normalized weekly intervals plus exception dates and provenance before claiming “open now.” Unknown hours get neither open boost nor closed penalty. With an explicit open-now filter, exclude unknowns but offer a labeled “hours unknown” alternative; on general discovery retain them. For spontaneous recommendations, known closed items can be excluded; for future planning evaluate hours at the intended time.

Use explicit `solo/group/unknown` session selection, not demographic guesses or message contents. Initial context is deterministic; learn time-block preferences only after ≥5 relevant outcomes in the same category, with smoothing and an off switch. A late-night food save does not prove the user visits restaurants at that hour. Do not import weather/calendar/location-history integrations for the first beta.

## 6. Diversity and exploration

Use **Maximal Marginal Relevance (MMR)** after retrieving a larger eligible pool: greedily pick the item maximizing `0.75*relevance - 0.25*max_similarity_to_selected`. Normalize relevance into [0,1] first; define similarity initially as `0.6*same_category + 0.4*tag_Jaccard`, with empty tag sets contributing zero. Later blend in embedding cosine similarity. This is a proposed parameterization of [Goldstein & Carbonell's MMR](https://aclanthology.org/X98-1025/), which trades relevance against redundancy.

- On a mixed-category rail, target ≥3 categories when supply allows, at most 4/12 from one category and no more than two consecutively. On a deliberately filtered category rail, diversify tags, neighborhood, creator and venue instead; do not override the user's filter.
- Event rail: at most two from one host/venue and one per recurring series. If fewer than 12 eligible items satisfy caps, relax category/host caps progressively; never relax visibility, hidden-item, time or capacity restrictions. Return fewer items if necessary.
- Reserve **one slot in 12 (~8%)** for beta exploration; increase to **two (~17%)** only after measuring hide and outcome rates. Randomize among eligible underexposed/new items with basic tag/context fit. No need to wait for social proof; no unbounded random off-topic items.
- Put one exploration draw in a slot uniformly sampled from positions 4–12, selecting its candidate uniformly from the eligible exploration pool after removing already selected items. Store `selection_probability=1/(9N)`, `exploration_pool_size=N`, `slot_probability=1/9`, step and final position. This is assignment probability before viewport exposure, not the probability the user actually sees it. With two slots, log sequential conditional probabilities without replacement. For shorter rails, use the actual available slot count; omit exploration if no slot remains.
- Stable random seed per request avoids list jitter. Suppress an item seen three times in seven days with no action for seven days; this is fatigue, not a negative taste label. Explicit hide persists until unhide. New inventory and reshuffles create new requests, not repeated impressions of the same render.

Diversity must operate on a pool larger than 12. Start by asking the existing RPCs for 50 candidates through `forYouPlaces` / `forYouEvents`, adding eligible fallback candidates if needed, and selecting 12 server-side. SQL and demo must still agree on pre-diversity scores and eligibility; the same deterministic diversity helper should handle both backends. Exploration is orthogonal to Claude reranking and should not depend on an LLM.

## 7. Evaluation

Maintain separate place and event reports, segmented by city, category, new/returning user and policy version. Start with observed counts and confidence intervals; 50 users cannot establish small lifts reliably. User counts in §3 authorize investigation, not automatic deployment.

| Metric | Exact starting definition | Use / limitation |
|---|---|---|
| Place Recall@k | Held-out newly saved eligible places in top k / all newly saved eligible places in the label window | k=12 for final rail, k=50/200 for retrieval; report coverage and excluded/unavailable positives. |
| Event Recall@k | Same, using successful joins to still-joinable events | Never recommend past events during replay or count failed/abandoned payments as joins. |
| NDCG@12 | `sum(binary_positive/log2(rank+1)) / ideal_DCG` | Binary save/join relevance initially; compute separately, macro-average by user; exclude zero-positive cases from NDCG and report their fraction. |
| Save rate per impression | Distinct qualified place impressions credited with a first new save / all qualified place impressions | Credit at most one exposure for each first save; unsave/resave loops must not inflate success. |
| Join rate per impression | Distinct qualified event impressions credited with a successful join / all qualified event impressions | Also report joins retained after 24 hours or until start, whichever comes first, and cancellation rate. |
| Hide rate | Distinct impressions credited with a hide / qualified impressions | Guardrail, separated by item type/category; unanswered impressions are not hides. |

**Attribution:** prefer a validated direct `impression_id` carried from card to detail/action; otherwise credit the latest same-user/same-item qualified impression within seven days for saves, and within `min(7 days, time until event start)` for joins. A direct parent must also meet the window. Store null for organic actions with no qualifying exposure; count them in overall engagement, not rail conversion. Capture the originating impression's surface/position, not the detail-page action surface, for rail metrics. Report raw save/join rates plus 24-hour retained outcomes. Mature labels before reporting; exclude recent immature windows from both numerator and denominator, and report cancellation/eligibility censoring rather than hiding it.

**Temporal offline test:** train on the first six weeks, validate the next week, test the following week using rolling time cutoffs; bootstrap uncertainty by user. Every user profile, rating, co-occurrence, eligibility and popularity feature must be computed before the simulated request. Do not build a taste profile with a held-out save and then “predict” it. For events, restrict candidate set to published, visible, future/available instances at request time; a future-created event is not a missed positive. Evaluate only users/items with eligible positives, alongside the excluded-user/item fraction. Compare rules, nearby/popularity fallback, content-only and challenger on the same candidate universe.

**Logging needed:** §2's qualified impression, user/item, server time, request ID, final position, policy/experiment, source, context/features and successful action with parent exposure are the minimum for online attribution and reranking evaluation on displayed items. Impression counts must include non-clicked visible cards; server-returned candidates alone are not impressions. Preserve all successful organic actions too, so held-out saves/joins are not limited to what the current recommender showed.

Full-catalog Recall@k additionally needs point-in-time candidate eligibility and challenger rankings: before model experiments, capture short-lived, owner-private evaluation snapshots of eligible IDs and item versions at sampled requests, plus rule/challenger top-200 lists. Candidate snapshots are **not impressions**. Use typed place/event FKs and profile cascading deletion for snapshot rows; purge at 30 days or sooner on consent withdrawal. Snapshot time/status/visibility/capacity and feature versions in trusted storage, then recheck current authorization before any replay output. The proposed interaction table alone cannot reconstruct historical opening status, capacity or edited/deleted inventory. Until snapshots exist, label metrics “logged-pool ranking only”; use synthetic eligibility fixtures for retrieval checks and do not claim unbiased full-catalog recall. Fit/test within retention windows or retain only non-identifying aggregates.

**Bias and rollout:** hold out users into stable control/treatment assignments, not alternating requests; keep an explicit rules control. Collect exploration probabilities from §6 to inspect position/exposure bias; do not apply inverse propensity weighting to deterministic rows with fabricated probability 1. Log the exact randomized policy and sampling support; clipped inverse propensity scoring is a later sensitivity analysis, not a substitute for a randomized online test. Model features exclude displayed position as a serving preference; use position to audit observation bias.

Set experiment duration/sample size from observed baseline and a predeclared minimum useful lift (initially 10% relative), rather than stopping at the first favorable day. Suggested promotion: offline NDCG@12 ≥5% relative improvement, retrieval recall not worse, and online primary save/join rate shows useful lift with uncertainty excluding material harm. Guardrails: hide rate increase <0.5 percentage points, no visibility failures, no material decline in category coverage, and recommendation p95 ≤300 ms excluding network/rendering. If underpowered, keep beta/shadow mode and interview users; do not declare a winner. Inspect examples of misses, repeated items and unsuitable event times weekly.

## 8. Privacy constraints

- **Other people's private saves are never a personalization/training signal.** Do not read `saved_places`, `saved_lists`, `saved_list_items`, private comparison rows or private save/view/hide histories across owners to build CF, neighbors, learned rankers, explanations or prompts. A backend service-role capability is not product permission. Own saves may personalize only their owner. Existing `places.save_count` is a deliberately published aggregate used by today's rules; retain that narrow established aggregate contract, never reconstruct identities or co-save edges from it.
- **Visibility precedes relevance.** Preserve `recommend_places` / `recommend_events` invoker behavior and current `can_view_place` / `can_view_event` rules. Later migrations extend visibility to `public`, `locals`, `trusted`, `followers`, `private`; use existing `is_local`, `is_trusted_local` and `is_mutual_follow`, not a home-city string or distance heuristic. Linked events inherit venue visibility; child tags, ratings and attendees follow the relevant visibility helpers. Hidden/removed content must never reappear through a vector index or stale cache.
- **Shared models use only globally public sources.** Even a locally authorized person's activity on a locals/trusted/followers/private item cannot enter a global model, neighbor explanation or externally hosted embedding index. Initially omit restricted items from shared indexes entirely; score authorized restricted items using viewer-scoped rules/content. Recheck permissions at retrieval, final hydration, explanation and click. Invalidate changed-visibility items from indexes/caches; retrieval IDs/scores must not leak hidden inventory even when cards are later filtered out.
- **No private-data leakage through “taste match.”** Public rating overlap is allowed; anonymous aggregate predictions require support thresholds and access-controlled aggregation. These thresholds reduce singling-out risk but do not constitute differential privacy. Never name a person based on private behavior. Explicit followed-person explanations remain limited to activity already visible through the current rules.
- **Private history stays private.** No friend/admin browsing of the new table; service processing is narrowly scoped to the owner's personalization, consented evaluation and retention/deletion. Shared-training opt-in permits only public-item exposure examples, minimal non-sensitive context, public rating/join outcomes and public collaborative features in a controlled training export. Strip user IDs from model inputs; retain a protected deletion mapping until the export is purged. Do not export raw `features`: rule/content scores can encode private saves. Shared training never consumes private saves, hides, views or private derived profiles. Aggregate evaluation may measure own-save outcomes without exposing histories or feeding those labels into another user's model. Document and enforce this allowlist before introducing any ML worker.
- **External AI is a separate boundary.** The inspected `candidatePayload` calls fields “public” but has no explicit public-visibility filter; upstream RLS can legitimately supply locals-only candidates, and `forYouPlaces` passes saved place names. Do not assume viewer authorization grants permission to export restricted listing text or private saved names. Keep `aiRerank` disabled until payload filtering/consent is explicit and tested; no external LLM/encoder gets private or restricted data by default. Recommendation-quality experiments do not require Claude.
- **No sensitive inference.** Do not use DMs (`messages`), reports, payment details, precise location history, inferred demographics, health/religion/sexuality or private social activity as taste features. Explicit interests can be used for their stated discovery purpose; avoid turning sensitive venue categories into inferred personal attributes. Store session context minimally and support reset/opt-out.
- **Deletion reaches derived state.** Apply §2's cascading ownership and deletion journal to history, category profiles, comparison rows, feedback, snapshots, neighbor caches and external exports. Remove affected users/items before serving rebuilt aggregates; retain only non-identifying evaluation summaries. Test closing-account races and revoked-local-access behavior, not just ordinary row deletion.

## 10. Open questions for the owner

1. **What counts as success initially?** Default: separate place saves and retained event joins; later add explicit “visited/enjoyed” feedback. Do not optimize clicks alone.
2. **Which city and 3–5 categories launch first?** Default: Columbus with its existing timezone, then validate category-specific supply/travel assumptions before expanding.
3. **Is explicit opt-in for recommendation history acceptable?** Default: off until consent, independent of anonymous analytics opt-out, with usable explicit-interest rules for nonparticipants.
4. **Should public ratings and public-event attendance contribute to shared models?** Default: defer shared training until the product notice/controls are clear; never include private saves even if model quality suffers.
5. **How much rating friction is acceptable?** Default: optional 1–3 same-category comparisons after an explicit visited/rated action; no forced ranking during onboarding and no replacement of public stars.
6. **Can hosts identify recurring series and join cutoffs accurately?** Default: only explicit host-managed series; future-only event rail until drop-in eligibility exists.
7. **Where will trustworthy opening hours/timezones come from?** Default: unknown remains unknown; no “open now” claims based on model guesses. Who maintains holiday exceptions?
8. **What may be sent to external AI providers?** Default: public listing text only; no saved names/restricted venue text or sensitive queries. Claude rerank remains off until this is resolved.
9. **What latency and operating cost can we afford?** Default: Postgres + scheduled jobs, p95 300 ms recommendation budget, no external live ranker until measured gains justify it.
10. **How should hides and revisits behave?** Default: hide until explicit unhide; already saved/rated places stay off discovery rails and can appear in a separate revisit surface; leaves/unsaves alone are not dislikes.
